## 1. 目標

讓使用者第一次在畫面上看見自己的 vault：欄 1 是 workspace、欄 2 是該 workspace 的文章、欄 3 是被選中那篇的正文，欄 4 的位置留給預覽面板。並且把「什麼算 workspace、什麼算文章」這五條硬規則放進負責檔案存取的那一層，讓畫面層永遠只收到已經整理好的清單。

## 2. User Stories

| ID | 故事 |
| :--- | :--- |
| **US-1** | 作為使用者，我要打開 App 就看到我的 workspace 清單與各自的文章數，這樣我知道東西都在 |
| **US-2** | 作為使用者，我要點一個 workspace 就看到它的文章，每一列看得到標題、什麼時候寫的、分類與標籤，這樣我不用打開檔案就找得到要改的那一篇 |
| **US-3** | 作為使用者，我要點一篇文章就直接開始寫，眼前只有正文 |
| **US-4** | 作為在 vault 裡放了 `.git`、`images/`、`README.txt` 的使用者，我要那些東西不冒充成 workspace 或文章，也不要被 App 動到 |
| **US-5** | 作為要開新主題的使用者，我要輸入一個名字就得到一個 workspace；名字有問題時我要知道是哪裡有問題，而不是得到一個奇怪的資料夾 |
| **US-6** | 作為第一次打開 App 的使用者，我要看到一句「從這裡開始」，而不是一片空白 |
| **US-7** | 作為每天寫作的使用者，我要 App 重開之後回到上次那一篇，不用每天重新找 |
| **US-8** | 作為還沒選文章的使用者，我不要看到一塊可以打字的空白區——對著沒有歸屬的編輯區打字，字會不知道存到哪裡去 |
| **US-9** | 作為用注音打字的使用者，我要在「新 workspace 名稱」欄位選字時按 Enter 只是確定選字，不是把表單送出去 |
| **US-10** | 作為只用鍵盤的使用者，我要按 Esc 再按 Tab 之後，焦點真的落在版面上另一個地方 |

## 3. 業務流程

### 3.1 App 啟動

```
App 啟動
   → 讀設定檔
        ├─ 沒有設定檔／不是合法 JSON → 用預設設定（不報錯）
        └─ 有 → 讀出「上次開啟的 workspace 與文章」
   → 列出 vault 底下的 workspace（依名稱排序，各帶文章數）
        └─ vault 資料夾不存在 → 空清單
   → 上次那個 workspace 還在？
        ├─ 不在／沒有記錄 → 什麼都不選；欄 2 與欄 3 都是空狀態
        └─ 在 → 選取它 → 列出它的文章
                → 上次那篇還在？
                     ├─ 不在 → 不選文章，欄 3 空狀態
                     └─ 在 → 選取它 → 載入正文到欄 3
```

### 3.2 一次「掃描 workspace」

```
讀出 vault 第一層的每一筆項目
   → 是資料夾嗎？（符號連結不算）
        └─ 不是 → 略過
   → 名字以 "." 開頭？ → 略過
   → 名字是保留名稱 images（不分大小寫）？ → 略過
   → 算一個 workspace
   → 數它第一層有幾篇文章（只數名字，不讀內容）
依名稱排序後交出
```

### 3.3 一次「掃描文章」

```
讀出該 workspace 第一層的每一筆項目
   → 是檔案嗎？（資料夾與符號連結都不算）
        └─ 不是 → 略過（images/ 與 2026/ 在這一步就沒了）
   → 副檔名是 .md 嗎？（不分大小寫，且檔名不能只有副檔名）
        └─ 不是 → 略過（README.txt、.DS_Store 在這一步沒了，而且沒有被動到）
   → 算一篇文章
依檔名排序
   → 逐篇讀檔 → 剝掉 front matter → 讀出 metadata（寬容）
        └─ 讀不到這個檔案 → 仍然列出：標題用檔名，標記 metadata 不完整
交出
```

### 3.4 一次「新增 workspace」

```
使用者輸入名稱並送出
   → 名稱是空的或只有空白 → 擋下（原因：名稱不可為空）
   → 名稱含 "/" 或 "\" → 擋下（原因：含路徑分隔字元）
   → 名稱是保留名稱（images、以 "." 開頭、"." 、".."；不分大小寫）→ 擋下（原因：保留名稱）
   → vault 第一層已經有這個名字（不分大小寫，資料夾或檔案都算）→ 擋下（原因：名稱已被使用）
   → 以上都過 → 建立資料夾 → 交出這個新 workspace（0 篇文章）
擋下時：沒有任何資料夾被建立
```

### 3.5 選取與還原

```
點一個 workspace
   → 它成為唯一被選取的 workspace
   → 列出它的文章
   → 清空欄 3（不選任何文章）
   → 把「上次開啟位置」寫回設定檔（workspace = 它，文章 = 無）

點一篇文章
   → 它成為唯一被選取的文章
   → 讀出它的正文（front matter 已剝離）放進欄 3
   → 把「上次開啟位置」寫回設定檔（workspace + 文章）
```

## 4. 驗收標準（Gherkin）

### Feature：什麼算一個 workspace（R-1、R-2、R-4、FR-1.1）

```gherkin
# TC-01
場景: 列出 vault 底下的資料夾，依名稱排序
  假設 vault 底下有資料夾 "work"、"Blog"、"Reading-Notes"
  當 系統列出 workspace
  那麼 得到 "Blog"、"Reading-Notes"、"work" 三個，依名稱排序

# TC-02
場景: 以點開頭的資料夾不是 workspace
  假設 vault 底下有資料夾 ".rustle"、".git"、"Blog"
  當 系統列出 workspace
  那麼 只得到 "Blog"

# TC-03
場景: 叫 images 的資料夾不是 workspace，不分大小寫
  假設 vault 底下有資料夾 "images"、"Images"、"Blog"
  當 系統列出 workspace
  那麼 只得到 "Blog"

# TC-04
場景: 檔案不是 workspace
  假設 vault 底下有檔案 "README.txt" 與 "Blog.md"，以及資料夾 "Blog"
  當 系統列出 workspace
  那麼 只得到 "Blog"

# TC-05
場景: 符號連結照它指向的東西算，指向 vault 外的不列出來
  假設 vault 底下有指向 vault 內資料夾的符號連結 "LinkedFolder"
  並且 vault 底下有指向 vault 內某個檔案的符號連結 "LinkedFile"
  並且 vault 底下有指向 vault 外資料夾的符號連結 "EscapingFolder"
  並且 vault 底下有指向 vault 外某個檔案的符號連結 "EscapingFile"
  並且 vault 底下有一個指向不存在位置的符號連結 "Dangling"
  當 系統列出 workspace
  那麼 "LinkedFolder" 是一個 workspace
  並且 "LinkedFile" 不是 workspace（它指向的是檔案）
  並且 "EscapingFolder"、"EscapingFile"、"Dangling" 都不在清單上，一列都沒有
# TC-05 於 code review 後依使用者裁決改寫。原文是「符號連結一律不算 workspace」，
# 但那條規則只在 workspace 這一側被實作，文章那一側接受連結，於是指向 vault 外的
# .md 變成一列點不開的文章。裁決：兩邊都允許連結，讓範圍檢查決定，指向 vault 外的
# 整筆排除——vault 內的連結在範圍檢查會解析連結之後已經可證明安全，而把連結整批
# 排除會讓使用者磁碟上真的存在的資料夾無聲消失。

# TC-06
場景: 每一個 workspace 帶著它的文章數
  假設 "Blog" 底下有 2 個 .md 檔與 1 個 images 資料夾，"Work" 底下沒有任何 .md 檔
  當 系統列出 workspace
  那麼 "Blog" 的文章數是 2，"Work" 的文章數是 0

# TC-07
場景: vault 裡沒有任何 workspace
  假設 vault 底下只有 ".rustle" 與 "README.txt"
  當 系統列出 workspace
  那麼 得到一份空清單（不是錯誤）

# TC-08
場景: vault 資料夾還不存在
  假設 vault 資料夾不存在
  當 系統列出 workspace
  那麼 得到一份空清單（不是錯誤）
```

### Feature：換文章不重建編輯區（NFR-3 的切換成本、FR-8.2）

```gherkin
# TC-60
場景: 開下一篇文章時，編輯區是同一個編輯區
  假設 編輯區裡是第一篇文章
  當 使用者開第二篇、再開第三篇、再回到第一篇
  那麼 每一次編輯區顯示的都是被開的那一篇
  並且 全程都是**同一個**可編輯節點——沒有任何一次是把編輯區拆掉重建

# TC-60a
場景: 同樣一份正文再送進來時，文件不動
  假設 編輯區裡是第一篇文章

  那麼 編輯區顯示第二篇
```

> 為什麼這條是驗收標準而不只是實作細節：需求文件 NFR-3 要求「開啟 10,000 字文章 < 100ms」，而每次切換都重建整個編輯區就是要付這筆成本；FR-8.2 則明文禁止「重建游標附近的畫面元素」，而拆掉重建是最徹底的那一種。「同一個可編輯節點」是這兩條在畫面上唯一驗得到的形式。
