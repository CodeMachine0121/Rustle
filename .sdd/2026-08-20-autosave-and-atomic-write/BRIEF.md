# 需求共識 — 自動儲存、原子寫檔與外部改動偵測

- **切片**：Wave 2，`feature/autosave-and-atomic-write`
- **日期**：2026-08-20
- **輸入**：需求文件 §3.3（R-10~R-12）、§3.2（R-6 的 `updated_at`）、FR-4.6、FR-8.4、§6.3 的 T-8／T-11、§7.3、§7.4「自動儲存踩進組字中」、NFR-4
- **狀態**：需求已定案（v0.3），本階段不回頭問使用者。文件留白處由本檔 §7「假設」一次裁決，並同步寫進 PR 說明

## 1. 這個切片要解決的問題

到目前為止，Rustle **從來沒有寫過任何一個位元到使用者的磁碟上**。front matter 切片交付了「讀進來、把區塊接回去」的知識，地基切片交付了一個能打中文的編輯區與一個會感知組字的去抖動器——但沒有人負責「什麼時候存」、「怎麼存才不會壞檔」、「檔案在我編輯的時候被別人改了怎麼辦」。

這三件事就是本切片：

1. **時機**（R-10）：停止輸入 1 秒後存；切換文章、切換 workspace、關閉視窗之前一定先存；**組字中一律不存**。
2. **手法**（R-11）：先寫暫存檔再 rename。當機、磁碟滿、權限不足都不能讓使用者的文章變成半截檔案。
3. **衝突**（R-12）：檔案在編輯期間被外部程式改動時，儲存前必須警示，讓使用者選「覆寫」或「重新載入」，**不得靜默覆蓋**。

外加一件使用者看得見的事：**標題列要顯示當前文章的標題與儲存狀態**（FR-4.6，UI 文案「已儲存」／「未儲存的變更」）。

這三件事有一個共同性質：**它們失敗的時候，使用者失去的是自己寫的東西**。所以本切片的判準不是「程式碼有沒有走過那條路」，而是「那個壞事有沒有被結構性地擋掉」。

## 2. 對誰有價值

| 角色 | 拿到什麼 |
| :--- | :--- |
| 使用者（James） | 打完字不用按 Cmd+S；切文章、關視窗不會掉字；停在候選視窗前想三秒鐘不會被存檔打斷；用 Obsidian 在另一邊改了同一篇時會被問，而不是被無聲蓋掉 |
| 使用者（機器當機那一次） | 文章檔案永遠是「舊的完整版」或「新的完整版」，不會是半截 |
| Wave 2 的版面與清單切片 | 一個「切換文章／切換 workspace 之前先存」的接縫，而且**繞不過去**——換文章的唯一入口本身就會先把上一篇存掉 |
| Wave 3 的預覽面板／建立文章切片 | 一個已經被證明會暫停倒數的儲存路徑，可以照抄同一個去抖動器的用法 |
| 後面每一個會寫檔的切片（建立文章、貼上圖片、metadata 編輯） | 一個「寫檔就是原子寫檔」的 repository 方法，沒有第二種寫法可選 |

## 3. 成功的樣子（可觀察的行為）

1. 在編輯區打字，停手一秒之後，磁碟上的檔案內容變成剛剛打的東西，而且 front matter 的 `updated_at` 換成現在的時間。
2. 連續打字 30 秒，磁碟上只會在停手之後被寫一次，不是每個鍵一次。
3. 用注音打字、盯著候選視窗超過 2 秒（T-8）：**沒有任何寫檔發生**，組字沒有被打斷；選完字之後，剩下的倒數才走完。
4. 點另一篇文章、換另一個 workspace、關閉視窗：上一篇的未存變更**在動作完成之前**已經進磁碟。關視窗那一次是真的寫完才關，不是「發出去就關」。
5. 標題列在有未存變更時顯示「未儲存的變更」，寫完之後變成「已儲存」。
6. 存檔過程中把電源拔掉（或程式被殺掉）：檔案是舊的完整內容或新的完整內容，**沒有第三種可能**。
7. 寫檔失敗（磁碟滿、沒有權限）：原本的檔案**逐位元不變**，不會留下垃圾暫存檔，畫面上看得出這次沒存成功。
8. 在 Rustle 開著的同時用別的編輯器改同一篇文章並存檔：Rustle 這邊要存的時候會告訴使用者「檔案被外部改動」，並給兩個選擇——覆寫、或重新載入。**沒有第三條路會讓它自己決定蓋掉。**
9. 儲存只改該改的：front matter 裡使用者自己加的欄位、鍵順序、註解、CRLF、BOM，存完之後都還在原位。

## 4. 邊界：本切片明確不做

| 不做 | 誰做 |
| :--- | :--- |
| 文章清單、workspace 清單、四區塊版面、「點文章載入正文」的互動 | Wave 2 `vault-workspace-and-article-listing`（同一個 wave，平行進行） |
| 建立文章對話框、真的建立新檔案 | Wave 3 `create-article-dialog` |

| 預覽面板、貼上圖片、篩選排序、捲動同步 | 各自的切片 |

| 「重新命名檔案」 | Wave 4 |
| front matter 的解析與接回本身 | 已由 Wave 1 `front-matter-and-body-loading` 交付，本切片只呼叫它 |
| 組字感知的去抖動器本身 | 已由 Wave 0 地基切片交付，本切片只使用它 |

**特別說明**：本切片**不做任何屬於版面的 UI**。它交付的畫面只有一個——標題列上的「文章標題 + 儲存狀態 + 外部改動時的兩個選擇」（FR-4.6 與 R-12 要求的東西）。四區塊、清單、空狀態都是隔壁切片的。

## 5. 為什麼「原子寫檔」不是加分項

一般的寫檔是 `open(檔案, 'w')` → 內容被截成 0 位元 → 一段一段寫進去。**檔案在這中間是壞的**：機器在這一刻當掉、磁碟在這一刻滿了、程式在這一刻被殺掉，使用者的文章就只剩前半段——而且舊的那份已經沒了。

正確做法是把「寫」與「換」分開：先寫一個暫存檔（寫壞了也只是壞在暫存檔上，原檔一個位元都沒動），確認整份內容落地，再用 `rename` 一次換掉。`rename` 在同一個檔案系統內是原子的：任何一個觀察者看到的都是舊檔或新檔，沒有中間狀態。

這件事對「每天寫文章」的產品不是選項，是 NFR-4 明文的「寫檔原子化」。

## 6. 例子（正常／邊界／例外）

### 6.1 什麼時候存（R-10、FR-8.4）

| 情境 | 動作 | 期望 |
| :--- | :--- | :--- |
| 正常 | 打一個字，停手 1 秒 | 寫檔一次 |
| 正常 | 連續打字，每 0.5 秒一個字，共 10 個字，然後停手 1 秒 | 只寫一次（停手之後那一次） |
| 邊界 | 打字後 0.4 秒開始組字，組字持續 10 秒 | 這 10 秒內完全不寫檔 |
| 邊界 | 承上，組字結束 | 再過 0.6 秒（剩下的時間）才寫檔，不是重新算 1 秒 |
| 邊界 | 組字中打字（`compositionupdate` 期間內容變了） | 倒數不開始；組字結束後才開始算 |
| 正常 | 有未存變更時切換到另一篇文章 | 切換完成前先把上一篇寫完 |
| 正常 | 有未存變更時切換 workspace | 同上 |
| 正常 | 有未存變更時關閉視窗 | **寫完才關**，不是發出去就關 |
| 邊界 | 沒有未存變更時切換文章／關視窗 | 不寫檔（不製造沒有意義的 `updated_at` 更新） |
| 邊界 | 沒有開啟任何文章時編輯區有輸入 | 不寫檔（無處可寫） |
| 例外 | 組字中要求立即寫檔（切換／關閉） | 等組字結束再寫；關視窗那條路徑會先讓編輯區失焦，讓輸入法自己收尾（T-11） |

### 6.2 怎麼存（R-11）

| 情境 | 動作 | 期望 |
| :--- | :--- | :--- |
| 正常 | 存一篇文章 | 檔案內容變成新的；同目錄不留任何暫存檔 |
| 邊界 | 目標檔案本身是唯讀的（`0444`） | 內容照樣換成新的（證明走的是 rename，不是打開原檔覆寫），而且**權限還是唯讀** |
| 邊界 | 文章是 vault 內指向另一個 vault 內檔案的符號連結 | 寫到連結指向的那個檔案，連結本身還是連結 |
| 例外 | 暫存檔寫不出來（目錄沒有寫入權限、磁碟滿） | 原檔**逐位元不變**；不留暫存檔；失敗要傳到畫面層 |
| 例外 | 名稱會逃出 vault（`../../etc/passwd`）或文章是指向 vault 外的符號連結 | 拒絕，什麼都不寫 |

### 6.3 外部改動（R-12）

| 情境 | 動作 | 期望 |
| :--- | :--- | :--- |
| 正常 | 檔案的修改時間與載入時記下的一致 | 正常寫入，並回報**新的**修改時間（下一次存才比得對） |
| 例外 | 不一致（別的程式改過） | **不寫入**，回報「偵測到外部改動」；記憶中的「上次已知修改時間」**不更新** |
| 邊界 | 承上，使用者還沒選，又打了幾個字 | **不再自動嘗試寫檔**（否則警示會被自己吃掉）；狀態停在「等使用者選」 |
| 正常 | 使用者選「覆寫」 | 以檔案**現在**的修改時間為預期，寫入成功；警示解除 |
| 正常 | 使用者選「重新載入」 | 交出磁碟上的正文；未存變更與警示一併清掉 |
| 例外 | 使用者選「覆寫」的那一瞬間，檔案又被改了 | **再次拒絕**（檢查發生在寫入前一刻，不是請求進來那一刻） |

### 6.4 存下去的東西長什麼樣（R-6／R-8）

| 情境 | 動作 | 期望 |
| :--- | :--- | :--- |
| 正常 | 存一篇有完整 front matter 的文章 | 只有 `updated_at` 的值變了；未知欄位、鍵順序、註解、其他欄位全部原位 |
| 邊界 | 檔案用 CRLF 換行、以 BOM 開頭 | 存完之後 CRLF 與 BOM 都還在 |
| 邊界 | 檔案完全沒有 front matter | 建立一個只有 `updated_at` 的區塊，正文原樣（見假設 A-4） |
| 例外 | front matter 是壞的 YAML | 正文照存、壞區塊逐字保留、`updated_at` 存不進去也不擋存檔 |

### 6.5 標題列（FR-4.6）

| 情境 | 期望顯示 |
| :--- | :--- |
| 有未存變更 | 文章標題 + 「未儲存的變更」 |
| 剛存完 | 文章標題 + 「已儲存」 |
| 寫檔期間又打了字 | 仍然是「未儲存的變更」 |
| 偵測到外部改動 | 警示文字 + 兩個選擇：「覆寫」、「重新載入」 |
| 寫檔失敗 | 失敗訊息，且變更仍算未儲存 |
| 沒有開啟文章 | 不顯示儲存狀態 |

## 7. 假設（需求文件留白處，本切片自行裁決）

| # | 空白 | 裁決 | 理由 |
| :--- | :--- | :--- | :--- |
| A-1 | R-12 說「mtime 與記憶中的不符」，那個「記憶中的」從哪來 | 從**讀檔那一刻讀到的修改時間**（`ArticleBody.lastKnownModifiedAt`），由畫面層原封帶回下一次儲存請求 | 契約已經備好這個欄位。用當下的牆上時鐘去猜「這個檔案應該多久沒被改」是猜的，比對讀到的值是量的 |
| A-2 | 偵測要在什麼時候做 | 問兩次，載重的那次在**真的要 rename 之前的最後一刻**，而且問與寫在同一個方法裡。**窗口只是縮到兩個 syscall，不是關閉**（見 §8） | 在請求進來那一刻檢查、在幾毫秒後才寫，中間那段空window 正是「檢查過了所以放心蓋」的漏洞。code review 實測過：只檢查一次的時候，一次外部寫入落在「寫暫存檔」那段裡就被靜默覆蓋 |
| A-3 | 「不得靜默覆蓋」要怎麼保證 | **寫檔方法沒有「不帶預期就寫」的形態**：`writeArticleFile` 一律要求呼叫方交出「我預期檔案現在是這個修改時間」。想覆寫的人必須先去讀檔案現在的修改時間，也就是必須先看見它改變了 | 「約定不要靜默覆蓋」擋不住忘記的人；沒有那個方法可以呼叫才擋得住。這也把 A-2 的空window 縮到最小（縮小，不是關閉）|
| A-4 | 沒有 front matter 的檔案，存檔時要不要長出一個 | **要**，長出一個只有 `updated_at` 的區塊 | §3.2 把 `updated_at` 列為必填、且「每次儲存時由 App 更新」。反方向的做法（沒有區塊就不寫 `updated_at`）會讓那些檔案永遠沒有更新時間，而 Wave 4 的排序要用它。代價寫在這裡：使用者手寫的純 Markdown 檔第一次被 Rustle 存過之後會多三行檔頭 |
| A-5 | `updated_at` 的時區形式 | UTC 的 ISO 8601 字串，也就是 `Z` 形式 | §3.2 要求「ISO 8601 含時區」，`Z` 是合法的時區標示。讀取路徑（`ArticleFile.lastModifiedAt`）已經是這個形式，兩邊一致比兩邊漂亮重要 |
| A-6 | 時間從哪裡來 | domain 借一個具名能力（`IClock`），實作在 infrastructure | domain 不碰 I／O，時鐘是最容易被偷偷直接讀系統時間的那一個。注入之後測試才驗得到「`updated_at` 真的來自時鐘」 |
| A-7 | 1 秒倒數用誰的實作 | 地基切片的 `CompositionAwareDebounce`，**不自己寫第二個計時器** | 它就是為 FR-8.4 而生的，而且已經有「暫停後接著走完剩餘時間」的測試。本切片補的是「儲存路徑真的繼承了這個行為」的測試 |
| A-8 | 「組字中要求立即儲存」（切換／關閉）該怎麼辦 | 等組字結束再寫；關視窗那條路徑先讓當前焦點元素失焦，讓輸入法自己收掉組字 | R-10「組字中一律不觸發儲存」與「關視窗前一定先寫」兩條都要滿足。失焦會讓輸入法確定組字並送出組字結束（T-11 的「先安全結束組字再切換」），所以不會卡住關不掉。實作時須確認所選 GUI 框架在失焦時確實會確定組字並發出組字結束 |
| A-9 | 關視窗要怎麼「寫完才關」 | 畫面層攔下這次關閉、把檔案寫完、再自己呼叫關閉 | 「寫完才關」的前提是關閉請求可以被攔下；實作時須確認所選 GUI 框架提供可取消的關閉事件。**變更真的上磁碟才關**：寫檔失敗或警示未回答時不關，讓使用者看見原因；第二次嘗試一律放行，所以磁碟滿的時候視窗不會關不掉（review 裁決）|
| A-10 | 儲存進行中又有輸入，怎麼算 | 仍算「未儲存的變更」；不打斷進行中的那一次寫檔，等它回來再排下一次 | 送出去的是當時那份正文。若寫完就無條件標成「已儲存」，中間打的字會被說成已經存了 |
| A-11 | 同一篇文章的兩次儲存重疊 | **排隊**，不並行 | 兩個 rename 互相追過去會讓「最後的內容」變成賭運氣 |
| A-12 | 外部改動警示還沒被回答，使用者就切換文章／切換 workspace／關視窗 | **一律不動作**：切換與關閉都被擋下（`blockedByUnansweredWarning`），畫面留在原地，警示與兩個選擇繼續在眼前 | 初版是「照切、不覆寫、放掉未存修改」。**review 裁決推翻它**：那等於一邊丟掉使用者的段落、一邊回報「已儲存」，與靜默覆蓋是同一種傷害，只是換一個方向。也評估過「把未存內容留著帶走」，同樣否決——沒有 UI 顯示的待處理狀態使用者無法處置，還會留給下一個切片一個沒人擁有的暗箱 |
| A-13 | 儲存失敗（磁碟滿、權限）要不要用具名的失敗原因傳回畫面層 | 不要，走既有的 `unexpected` | 地基切片定案的失敗原因清單不為此擴張。失敗訊息本身足以顯示，畫面層不需要對這種失敗分流 |
| A-14 | 暫存檔叫什麼、放哪 | 與目標檔案**同一個目錄**，名字是 `.{檔名}.{隨機}.rustle-temporary` | 同目錄才保證同一個檔案系統，`rename` 才是原子的。開頭一個點且不以 `.md` 結尾，所以不會出現在文章清單裡（R-3／R-5） |
| A-15 | 暫存檔要不要 `fsync` | 要，rename 之前先把資料落到磁碟 | 不 fsync 的話「rename 完成但內容還在快取裡」在斷電時會得到一個長度正確、內容為空的檔案。這正是 R-11 要防的事 |
| A-16 | 原檔的權限要不要保留 | 要，rename 之前把暫存檔的權限設成原檔的權限 | 否則每存一次檔就把使用者設定的權限改成預設值——那也是「儲存改了不該改的東西」 |
| A-17 | 儲存狀態的文案 | 「已儲存」／「未儲存的變更」，照通用語言地圖 `updated_at` 那一列 | 詞彙表已經定了，不自創同義詞 |
| A-18 | 目標檔案不存在時（例如文章在別處被刪了） | 當一般失敗處理（`unexpected`），不自動建檔 | 建立檔案是別的切片的需求，而且「檔案不見了就幫你建一個」會把使用者的刪除動作救回來 |
| A-19 | 寫檔**失敗**（不是外部改動）時要離開文章／關視窗 | **第一次擋下並顯示原因，第二次刻意再試就放行**（放行時未存修改被放掉） | review 裁決。全 App 一條規則：**會毀掉東西的動作要有第二次、知情的嘗試**。這同時解掉兩難的兩邊——使用者不會被磁碟滿困在一篇文章裡，也不會因為一次不知情的點擊失去一段文字。實作沿用關視窗那個「已經試過一次」的概念，不另立第二套機制 |

## 8. 已知不做、但要記錄的取捨

- **本切片交付的儲存路徑今天在 App 裡跑不到端到端**：沒有 vault 掃描、沒有文章清單，所以 App 裡沒有「開啟的文章」可以存。這是切片邊界的必然結果（隔壁切片正在做那一半）。本切片的驗收因此落在通道層、物件層與真實檔案系統上，並在標題列留下「沒有開啟文章」的狀態。
- **硬連結仍然穿得過範圍檢查**（front matter 切片已記錄，見發佈檢查清單 S-3）。本切片沒有改善它，因為 `realpath` 對硬連結無能為力。
- **建立檔案路徑的符號連結檢查仍然是缺口**：本切片只寫「已經存在的檔案」，所以 `realpath` 用得上；建立新檔（父資料夾解析）留給建立文章切片。
- **沒有寫檔失敗的重試**。失敗就顯示失敗、變更留在編輯區、下一次輸入會再排一次儲存。自動重試會把「磁碟滿」變成每秒一次的無效寫檔。
- **外部改動的窗口是縮小，不是關閉**（A-2）。`stat` 與 `rename` 之間仍有兩個 syscall 的寬度，落在那裡的外部寫入還是會被蓋掉。要真的關閉需要 file locking 或 `renameat2`，兩者都超出本切片（也超出「個人單機工具」的合理成本）。寫在這裡是為了不讓人把它讀成「已經完全封閉」。
