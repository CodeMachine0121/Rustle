# 側欄分區與狀態過濾 — Requirements Brief

## Goal

左欄從「一排 workspace」變成**分區的側欄**：Workspace 一區、狀態一區、標籤一區，每一區都能折疊起來。點狀態或點標籤就會過濾右邊的文章清單，兩邊同時選時要同時符合。另外新增一個「All Notes」入口，讓寫作者一次看到 vault 裡所有 workspace 的文章。同時把現有的「分類」這個概念整個退場，換成**狀態**——一篇文章只有一個狀態，而且只能是固定四個之中的一個。

目的是讓寫作者不用記得文章放在哪個 workspace，也能靠「這篇進行到哪了」和「這篇講什麼」兩個角度把文章找出來。

## Requirements

### 側欄的分區

- 左欄分成三個區塊，由上到下：**Workspace**、**狀態**、**標籤**。
- 每個區塊的標題可以點，點一下把該區的內容折疊起來，再點一下展開。
- 折疊或展開的選擇要**記住**，關掉 App 再開還是同一個樣子。
- 折疊 Workspace 區不會改變「現在選的是哪個 workspace」，文章清單不受影響。
- 在 Workspace 區之上有一個 **All Notes** 入口，與「選某一個 workspace」互斥。

### 狀態

- 一篇文章**只有一個**狀態。
- 狀態只能是這四個之一：**Active**、**On Hold**、**Completed**、**Dropped**。寫作者不能自己新增或改名。
- 文章**可以沒有狀態**。建立文章時不強迫選。
- 狀態在建立文章與事後編輯文章 metadata 的同一個表單裡設定，跟標題、標籤放在一起。
- 若文章的檔案裡記著一個不是那四個之中的狀態，這篇一律當成「沒有狀態」，而且**檔案裡原本那行字不能被改掉或清掉**。

### 側欄的狀態區

- 狀態區固定列出五列：Active、On Hold、Completed、Dropped，以及**未設定**。
- 每一列右邊顯示符合的文章篇數。
- 五列**永遠都在**，篇數是 0 也照樣顯示。
- 同一時間**最多只能選一個**狀態；再點一次已選的那一列就取消選取。

### 側欄的標籤區

- 標籤區列出目前範圍內文章用過的所有標籤，每個標籤右邊顯示篇數。
- 標籤**可以同時選多個**。
- 選了多個標籤時，文章要**每一個都有**才算符合。
- 沒有任何文章帶標籤時，標籤區顯示「還沒有標籤」。

### 過濾

- 選了狀態就只留下該狀態的文章；選了標籤就只留下帶著那些標籤的文章。
- 兩邊都選時，文章要**同時符合狀態與所有選中的標籤**。
- 過濾後一篇都不剩時，文章清單要說「沒有符合的文章」，不能只留一片空白。
- **正在編輯的那篇文章的列永遠留著**，不管它符不符合當前的過濾。
- 側欄的過濾與文章清單既有的**文字篩選框**是兩套獨立的收窄方式，同時生效時互相疊加。
- 文字篩選框**不再比對分類**。

### All Notes

- 選了 All Notes 之後，文章清單列出 vault 裡**所有 workspace** 的文章。
- 這時側欄狀態區與標籤區的篇數，是**跨所有 workspace** 算出來的。
- 這時文章清單的每一列要看得出這篇屬於哪個 workspace。
- 在 All Notes 之下**不能建立新文章**——按下建立時擋下來，並告訴寫作者要先選一個 workspace。

### 分類退場

- 建立文章與編輯 metadata 的表單裡**不再有分類欄位**。
- 文章清單不再顯示分類。
- 舊文章檔案裡已經寫著的分類，**原樣保留在檔案裡**，Rustle 不顯示它、不修改它、不刪除它。也不把它搬成標籤或狀態。

## Examples (Specification by Example)

每個例子只列會影響結果的資料。

### Rule: 一篇文章只有一個狀態，且只能是那四個之一

| # | Given (only relevant data) | When | Then |
|---|---|---|---|
| 1 (happy) | 建立文章時選了「Active」 | 文章建立完成 | 這篇的狀態是 Active |
| 2 (boundary) | 建立文章時沒有選狀態 | 文章建立完成 | 這篇沒有狀態，並被算進側欄的「未設定」那一列 |
| 3 (boundary) | 一篇狀態是 Active 的文章 | 在編輯 metadata 的表單裡改成 Completed | 這篇的狀態變成 Completed，Active 不再成立 |
| 4 (exception) | 檔案裡的狀態寫著「進行中」 | 開啟這篇 | 當成「沒有狀態」；存檔後檔案裡「進行中」那一行**原樣還在** |

### Rule: 側欄的狀態區固定五列並顯示篇數

| # | Given (only relevant data) | When | Then |
|---|---|---|---|
| 1 (happy) | 目前範圍內有 3 篇 Active、1 篇 On Hold、2 篇沒有狀態 | 看側欄的狀態區 | Active 3、On Hold 1、Completed 0、Dropped 0、未設定 2 |
| 2 (boundary) | 目前範圍內一篇文章都沒有 | 看側欄的狀態區 | 五列都還在，篇數全部是 0 |
| 3 (boundary) | 狀態區已經選著 Active | 再點一次 Active 那一列 | 取消選取，文章清單回到沒有狀態過濾的樣子 |
| 4 (exception) | 狀態區已經選著 Active | 點 Completed 那一列 | 只剩 Completed 被選著，Active 自動放掉 |

### Rule: 選狀態或標籤就過濾文章清單，兩邊都選時要同時符合

| # | Given (only relevant data) | When | Then |
|---|---|---|---|
| 1 (happy) | 文章 A 是 Active、文章 B 是 Completed | 選狀態 Active | 只剩文章 A |
| 2 (happy) | 文章 A 是 Active 且帶標籤 work、文章 B 是 Active 但沒有標籤 | 選狀態 Active 再選標籤 work | 只剩文章 A |
| 3 (boundary) | 文章 A 帶標籤 work 與 bug、文章 B 只帶 work | 同時選標籤 work 與 bug | 只剩文章 A（每個選中的標籤都要有） |
| 4 (boundary) | 選著標籤 work 與 bug | 取消選取標籤 bug | 只剩「帶 work」這一個條件 |
| 5 (exception) | 範圍內沒有任何一篇是 Active | 選狀態 Active | 文章清單顯示「沒有符合的文章」 |
| 6 (exception) | 正在編輯的文章是 Completed | 選狀態 Active | 那篇文章的列**還留在清單上** |
| 7 (boundary) | 選著狀態 Active，文字篩選框打了「桌面」 | 看文章清單 | 只剩「狀態是 Active」**且**「標題或標籤含有『桌面』」的文章 |

### Rule: All Notes 跨所有 workspace

| # | Given (only relevant data) | When | Then |
|---|---|---|---|
| 1 (happy) | Vault 有 Blog 與 Work 兩個 workspace，各有文章 | 選 All Notes | 兩個 workspace 的文章全部出現在清單上 |
| 2 (happy) | 在 All Notes 之下 | 看文章清單的某一列 | 那一列看得出這篇屬於哪個 workspace |
| 3 (happy) | Blog 有 2 篇 Active、Work 有 1 篇 Active | 在 All Notes 之下看狀態區 | Active 顯示 3 |
| 4 (boundary) | 在 All Notes 之下選著狀態 Active | 改成選 workspace「Blog」 | 清單只剩 Blog 裡狀態是 Active 的文章 |
| 5 (exception) | 在 All Notes 之下 | 按「新文章」 | 擋下來，並告訴寫作者「請先選一個 workspace」，不建立任何檔案 |

### Rule: 分區可以折疊，而且記得

| # | Given (only relevant data) | When | Then |
|---|---|---|---|
| 1 (happy) | 標籤區是展開的 | 點標籤區的標題 | 標籤區的內容收起來 |
| 2 (happy) | 標籤區是收著的 | 關掉 App 再開 | 標籤區還是收著的 |
| 3 (boundary) | 目前選著 workspace「Blog」 | 折疊 Workspace 區 | 還是選著 Blog，文章清單不變 |
| 4 (boundary) | 狀態區收著，而且選著狀態 Active | 看文章清單 | 過濾照樣生效（收起來只是看不到，不是取消） |

### Rule: 分類整個退場，但檔案裡的字不動

| # | Given (only relevant data) | When | Then |
|---|---|---|---|
| 1 (happy) | 舊文章的檔案裡分類寫著「技術筆記」與「桌面開發」 | 開啟這篇、改幾個字、存檔 | 畫面上完全看不到分類；檔案裡那兩行分類**原樣還在** |
| 2 (happy) | — | 打開建立文章的表單 | 沒有分類欄位，改成有一個狀態欄位 |
| 3 (boundary) | 一篇文章的分類是「技術筆記」，標題與標籤都沒有這幾個字 | 在文字篩選框打「技術筆記」 | 這篇**不會**被列出來 |
| 4 (boundary) | 舊文章的檔案裡有分類 | 在編輯 metadata 的表單裡把狀態改成 Active 並存檔 | 狀態被寫進去，分類那幾行**原樣還在** |

## Out of Scope

以下是範例 App 有、但**不屬於這一條**的東西，各自另開切片：

- 文章清單的卡片顯示正文摘要
- 文章範本
- 待辦完成度（例如「2 of 4」）
- 把文章釘選到清單頂端
- 編輯器上方的前進／後退
- 編輯器上方的「編輯／分割／預覽」三段切換
- 編輯器的行號與目前行高亮
- 在標題下方直接改 workspace／狀態／標籤（不開表單）
- **純外觀**（重點色、字級、間距、圓角、卡片與膠囊樣式）——由 `feature/visual-theme-refresh` 這條分支獨立處理，不在本切片的驗收範圍內
- 全文搜尋
- 巢狀的 workspace（workspace 的樹狀結構）
- 把 vault 換到別的位置

## Open Decisions

留給 PRD 作者決定的：

- **狀態的畫面文字要用英文還是中文。** 這份 brief 用的是英文的 Active／On Hold／Completed／Dropped，與範例 App 一致；專案其他地方的區塊標題也是英文大寫（WORKSPACES／ARTICLES）。但表單裡的欄位提示是中文。PRD 要把「畫面上到底顯示哪一種」釘死，並同步進詞彙地圖。
- **「未設定」那一列的畫面文字。** 同上，要決定用哪一種語言，以及是否要用別的說法（例如「沒有狀態」）。
- **標籤區要不要排序、怎麼排。** 按篇數多到少、按名稱、還是按最近用過。本 brief 沒有規定。
- **標籤區的篇數是否受狀態過濾影響。** 例如已經選著 Active 時，標籤 work 顯示的是「所有 work 的文章數」還是「Active 且 work 的文章數」。兩種都說得通，PRD 要選一種。
- **在 All Notes 之下，文章清單的排序基準。** 跨 workspace 之後，同一個排序條件下的並列要怎麼決定先後。
- **狀態區與標籤區的選取是否跟著 workspace 切換而清空。** 從 Blog 切到 Work 時，原本選著的 Active 與 work 要保留還是放掉。

## Context / Background

### 為什麼是這五個規則

出發點是一張範例 App 的畫面：它的左欄不是一排資料夾，而是 All Notes ／ 範本 ／ Notebooks ／ Status ／ Tags ／ Trash 六個分區。寫作者被問到時明確表示：Rustle 的 workspace 就對應它的 Notebooks，而它的 Status 與 Tags 這兩個「用來收窄清單的角度」是他真正想要的東西。

### 為什麼分類要換成狀態，而不是兩個都留

分類原本的語意是「這篇屬於哪個分類」，可以有多個、詞彙自由。寫作者判斷這件事在實際使用上跟標籤重疊了——「這篇講什麼」已經有標籤在管，再多一個自由文字的歸類欄位只會製造同義詞漂移。真正缺的是另一個維度：**這篇進行到哪了**。所以分類直接讓位給狀態，不並存。

### 為什麼舊檔案的分類要原樣留著，而不是搬過去

寫作者選的是「完全不動它」。理由是狀態與分類語意不同：把「技術筆記」當成狀態沒有意義，把它變成標籤又會替寫作者做他沒有要求的決定。而 Rustle 本來就承諾「檔案裡不認識的欄位原樣保留」，所以分類退場之後它自然落進這條既有的承諾裡——不需要任何一次性的資料搬遷，也不會有搬遷做壞的風險。

### 與需求文件的衝突（需要寫作者自己處理）

需求文件是這個專案需求的唯一真實來源，而且**任何切片都不得修改它**。這份 brief 推翻了它上面關於分類的多條敘述——分類的欄位定義、文章清單要顯示分類、文字篩選要比對分類、建立文章的表單要有分類欄位、分類要有自動補全。

這份 brief 記錄的是寫作者當下的裁決；需求文件的改版由寫作者本人負責，時間點不影響本切片開工。

### 這一條與外觀那一條的關係

寫作者要求行為與外觀兩件事平行進行，各自一條分支。本切片只負責**行為**：分區、折疊、狀態、過濾、All Notes、分類退場。它會需要為新的側欄結構寫樣式，但「顏色與尺度長什麼樣」不由它決定——它一律引用外觀那條分支定義的設計變數名稱，兩邊在合併時才碰頭。
