# 需求共識 — 貼上圖片

- **切片**：`feature/paste-image-to-workspace`（Wave 4）
- **輸入**：需求文件 §3.4（R-13 ~ R-19）、§4.7（FR-6.1 ~ FR-6.10）、§4.6 的 FR-5.9、§6.2（FR-8.1、FR-8.7）、§6.3（T-8、T-11 的相鄰項）、§7.3（讀取剪貼簿圖片、PNG 編碼、格式轉換、UUID 產生的選型與安全基線）、§7.4（**第一列陷阱：預覽面板載不出圖片**、第五列陷阱：貼上圖片與 undo 的不對稱）、NFR-2、NFR-4、NFR-7
- **需求已定案**，本檔不是訪談紀錄，而是「這個切片要交付什麼、邊界在哪、留白處我怎麼裁決」的共識書面化。歧義一律在下方 §7 記為假設，不停下來等答案。

---

## 1. 這個切片要解決的問題

寫文章的人截了一張圖，想把它放進正在寫的段落裡。今天他必須：自己找一個資料夾、自己想一個檔名、自己把檔案存過去、自己打出 `![](...)`、自己確認路徑對不對。這五件事沒有一件跟「寫文章」有關。

這個切片要讓那五件事消失成一個動作：**在編輯區按貼上，圖片就在那裡了**。檔案落在這個 workspace 的 `images/`，正文裡多一行相對路徑的 Markdown，右邊的預覽面板立刻把圖畫出來。中間不問任何問題。

## 2. 對誰有價值

| 誰 | 價值 |
| :--- | :--- |
| 寫文章的人（唯一使用者） | 截圖到文章裡是一個動作。而且正文存的是相對路徑，所以這篇文章連同 `images/` 搬去 Obsidian、丟上 Git、餵給 Hugo 都還是同一張圖 |
| 未來的自己 | `images/` 是 workspace 共用的資料夾、檔名是 UUID，所以不會有「哪張圖被哪篇引用」的命名決策債，也不會有撞名 |
| 下游切片 | `rustle:` protocol handler 在本切片第一次有真正的呼叫者。捲動同步切片會拿到「預覽裡真的有圖片高度」這個現實 |

## 3. 成功的樣子（可觀察的行為）

1. 選好一篇文章，在編輯區按 `Cmd+V`：`{workspace}/images/` 裡多一個 UUID 名字的檔案，游標處多一行 `![](images/{uuid}.png)`，預覽面板裡看得到那張圖。全程沒有任何對話框。
2. 檔案裡存的永遠是 `images/{uuid}.png` 這種**相對路徑**。預覽能顯示它，是因為**渲染那一刻**才把 `src` 改寫成 `rustle://vault/{workspace}/images/{uuid}.png`；改寫不落地、檔案裡永遠看不到絕對路徑或 `file://`。
3. 一次貼上在 undo 歷史裡是**一步**：按一次 undo，語法整段不見，**檔案還在**。
4. 沒有選取文章時，貼上圖片這件事根本不存在（沒有編輯區可以按貼上）。
5. 組字中按貼上，那一次按鍵屬於輸入法，不落檔、不插入。
6. 剪貼簿裡沒有圖片時，貼上就是平常的貼上，一個字都不差。
7. 寫檔失敗（磁碟滿、權限不足）時，正文**一個字都不會多**，畫面上出現一行說明失敗原因的非阻斷訊息。
8. 大圖（>10MB）寫檔期間畫面不凍結，而且看得出來「正在存」。
9. `rustle:` 只服務 vault 底下的圖片。`..`、絕對路徑、URL 編碼過的分隔字元、指向 vault 外的符號連結、`.md` 檔、`.rustle/settings.json`——一律拒絕。（URL 編碼過的 `..` 是特例：位址解析器會先把那個步階折疊掉，所以它連成為名字的機會都沒有，見 §5.3 第 21 列。）

## 4. 邊界：本切片明確不做

| 不做 | 為什麼 |
| :--- | :--- |
| 刪除圖片、清理孤兒圖片 | R-18 明文不做。刪文章不刪圖、undo 貼上不刪檔。`images/` 是 workspace 共用的 |
| 拖放（drag and drop）圖片、從檔案選擇器插入圖片 | 需求只寫「貼上」（FR-6.1）。多一條入口就多一條要驗的路徑，而它不在任何一條需求上 |
| 圖片縮放、壓縮、產生縮圖、EXIF 清理 | 需求沒有要求。R-15／R-16 只講格式，不講尺寸 |
| 預覽面板的分隔線（FR-5.6）與捲動同步（FR-5.8） | 屬於 `feature/list-controls-and-preview-geometry` |
| metadata 編輯、刪除文章／workspace | 屬於 `feature/metadata-editing-and-destructive-operations` |
| 正文裡手寫的 `<img src="images/x.png">` 也改寫 | 見假設 A-12 |
| 硬連結（hard link）的範圍檢查 | 發佈檢查清單 S-3，全專案未關閉且**這個方法解不了**。本切片不假裝關掉它，見 §8 |

## 6. 這個切片跟輸入法的關係

| 條目 | 本切片的責任 |
| :--- | :--- |
| FR-8.1（組字中不得修改文件） | 貼上是「修改文件」最粗的一種。組字中一律不做，那次事件不攔 |
| FR-8.7（組字中的 `Cmd+V` 屬於輸入法） | FR-6.10 就是它的特例，由 `CompositionState` 這個共用閂判斷，不自己接 composition 事件 |
| T-8（組字停留 > 2 秒） | 本切片不新增任何計時器，所以不會踩進組字。忙碌指示是「有沒有寫檔在進行」，與時間無關 |
| T-11（組字中切換文章） | 本切片不動切換路徑 |
| 發佈清單「新增任何綁 `Cmd+V` 的快捷鍵」 | 本切片新增一個 paste 事件處理器，**必須重跑 T-1 ~ T-12** |

## 7. 假設（需求文件留白處，本切片自行裁決）

| # | 留白 | 裁決 | 理由 |
| :--- | :--- | :--- | :--- |
| A-1 | 「剪貼簿有沒有圖片」誰來判斷 | **畫面層**看貼上事件自己帶的剪貼簿內容（有沒有圖片類型的項目）決定要不要攔這次貼上；**負責檔案存取的那一層**才是真正讀剪貼簿、決定格式與位元的一方 | FR-6.7 要求沒有圖片時「行為不變」，而一般文字貼上是編輯區的預設行為——先問負責檔案存取的那一層再決定要不要攔下這次貼上已經來不及（跨層呼叫是非同步的）。通道的請求形狀也已經定案為只帶 workspace 名稱，位元不從畫面層來 |
| A-2 | 靜態 GIF 算不算「可無損轉 PNG 的點陣格式」 | **轉 PNG** | R-16 點名保留的是「**動畫** GIF」。一張靜態 GIF 轉 PNG 沒有任何損失，也不會失去動畫特性 |
| A-3 | 動畫 WebP 怎麼辦（R-16 只點名「WebP 靜態」轉 PNG） | **保留原格式** | 需求給的理由是「轉 PNG 會失去動畫特性」，那個理由對動畫 WebP 一字不改地成立 |
| A-4 | 認不出的檔案型別（`.heic`、`.psd`、`.avif`…） | **不算圖片**，走一般文字貼上——**畫面層連那次貼上事件都不接手**，所以那真的是編輯區自己的預設貼上（實作期間修正：原本會先攔下再自己插入文字） | 需求列舉的是 JPEG/BMP/TIFF/WebP/GIF/SVG。把認不出的東西當圖片存進 `images/`，等於把 `images/` 變成雜物櫃，而且預覽也顯示不出來 |
| A-5 | 一次貼上「多張圖片」在 macOS 上真的拿得到幾張 | 管線支援 N 張、依序落檔、各一行語法；但 macOS 剪貼簿經常只暴露「一張點陣圖」或「第一個檔案 URL」，所以實務上一次通常是一張；實作時須確認所選剪貼簿存取方式一次拿得到幾張 | 這是平台限制，不是設計限制。FR-6.6 的行為由服務層完整實作並驗證（餵兩張進去就落兩個檔、插兩行、一步 undo）；能不能一次撈到兩張取決於所用的剪貼簿存取方式。誠實寫在這裡，也寫進 PR |
| A-6 | 多張圖片時游標停在哪 | **最後一張**的 alt 位置 | 一般貼上結束後游標在貼上內容的尾端；FR-6.4 要的是「想補說明可以直接打字」，最後一張是寫作者眼睛所在的地方 |
| A-7 | 多張圖片之間怎麼分隔、要不要自動補空行 | 以換行分隔，插入點就是游標處，不自動補空行 | FR-6.6 只說「各插入一行語法」。自動補空行是替寫作者改他的排版 |
| A-8 | 忙碌指示只在 >10MB 出現，還是一律出現 | **一律出現**（有寫檔在進行就顯示） | FR-6.9 要的是「大圖要有指示、且不得凍結」。一律顯示是它的超集，而且「什麼時候算大」是一條沒有人需要的規則 |
| A-9 | 畫面層看到圖片、負責檔案存取的那一層卻回「沒有圖片」 | 不插入任何圖片語法，改插入 paste 事件當時的純文字。**只適用於「剪貼簿確實沒有圖片」這一種答案**；寫檔失敗一個字都不插入（實作期間修正，見 A-13） | 這是剪貼簿在兩者之間被換掉的競態。已經攔下這次貼上就回不去編輯區的預設行為，而把當時的文字放進去最接近 FR-6.7 的「行為不變」 |
| A-10 | `rustle:` URL 的形態 | `rustle://vault/{workspace}/images/{fileName}`，host 固定 `vault`，兩段名字各自 URL 編碼 | 沿用預覽切片 PRD 舉例時就寫下的形態。workspace 名字可能有空白與中文，所以名字放 path 而不是 host（host 會被小寫化與 punycode 化） |
| A-11 | handler 服務的範圍 | 只服務 `{workspace}/images/{單一段檔名}`，且副檔名必須是圖片副檔名 | 這個 scheme 存在的唯一理由是 FR-5.9。任何一段多出來的能力都是白送的攻擊面——`.md` 與 `.rustle/settings.json` 都在「多出來的能力」裡 |
| A-12 | 正文裡手寫的 `<img src="images/x.png">` 要不要改寫 | **不改寫**（原樣保留，所以顯示不出來） | 改寫發生在 Markdown 的圖片 token 上；raw HTML 是另一條路徑。R-17 的相對路徑是 App 自己寫進正文的 Markdown，手寫 HTML 不在任何一條需求上。留白處選「不動使用者寫的東西」 |
| A-13 | 多張圖其中一張失敗 | 整次貼上不插入任何語法 | R-19 的字面是「不插入任何 Markdown 語法」。插一半會讓寫作者看到一行對的、一張不見的 |
| A-14 | 失敗訊息顯示在哪 | 編輯區欄位上方的一行非阻斷訊息，與「正在存」共用同一個位置 | 標題列已經住著儲存狀態（自動儲存切片），把圖片的訊息塞進去會讓那一行同時說兩件事 |

## 8. 已知不做、但要記錄的取捨

| 取捨 | 說明 |
| :--- | :--- |
| **貼上與 undo 的不對稱**（§7.4 第五列） | 檔案已經落地，undo 只退回文字。這是 R-18 的必然結果，也是刻意選擇：`images/` 共用，同一張圖可能被別篇引用，誤刪的代價遠高於留下孤兒檔案。寫進 README 的「已知行為」與發佈檢查清單 |
| **硬連結**（S-3） | 本切片新增第五條寫入路徑（`images/{uuid}`），它跟建立文章一樣以「不存在才建立」開檔，所以寫不進一個既有的硬連結；但 `images/` 自己若是硬連結（同一份 inode），`realpath` 看不出來。**這條沒有被本切片關掉**，發佈檢查清單的 S-3 照原樣留著，只補上本切片這條路徑的現況 |
| **格式轉換可能依賴原生函式庫** | R-16 需要把 JPEG／BMP／TIFF／靜態 WebP／靜態 GIF 轉成 PNG，所選的影像處理依賴可能帶進平台專屬的二進位檔。截圖那條主路徑**完全不碰格式轉換**（點陣圖已經是 PNG），所以就算格式轉換在某台機器上不可用，最常走的路也不會壞 |
| **一次貼上只讀一次剪貼簿** | 負責檔案存取的那一層讀的是「現在」的剪貼簿，不是 paste 事件那一刻的。兩者之間被換掉就是 A-9 那條競態 |
