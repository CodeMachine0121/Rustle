# 需求共識 — Tab / Shift+Tab 縮排行為

- **切片**：Wave 1，`feature/tab-indentation-behavior`
- **日期**：2026-08-20
- **輸入**：需求文件 §5 全部（§5.1 行為矩陣、§5.2 FR-7.1 ~ FR-7.7）、FR-4.3、§6.2（FR-8.1／FR-8.3／FR-8.7）、§6.3（T-5／T-7）
- **狀態**：需求已定案（v0.3），本階段不回頭問使用者。需求文件留白處由本檔第 7 節裁決，並同步寫進 PR 說明

## 1. 這個切片要解決的問題

需求原文只有一句：「按下 tab 時只能做縮排的動作，同理 shift+tab 也要可以 work」。這一句是產品**三個不妥協的主張之一**（專案總覽 §1：「鍵盤行為可預期。Tab 只做縮排」），而需求文件 §5 已經把它展開成一張可驗收的行為矩陣。

問題在於：**編輯器目前刻意沒有綁 Tab。** 地基切片把 Tab 留空是有理由的——一個吃掉 Tab 的可聚焦元件會把鍵盤使用者關在裡面出不來，這是 W3C 的無障礙要求，也是一般編輯器元件預設不綁 Tab 的原因。所以本切片不是「加一個快捷鍵」，而是**同時**解決三件互相拉扯的事：

1. Tab 一定要縮排，而且行為要跟需求文件那張矩陣**逐格一致**。
2. Tab 被吃掉之後，鍵盤使用者仍然要能離開編輯區。
3. 使用者正在用輸入法選字時，Tab 不屬於 App——有些輸入法用 Tab 翻候選頁。

## 2. 對誰有價值

| 角色 | 拿到什麼 |
| :--- | :--- |
| 使用者（James，每天用中文寫文章、寫巢狀清單） | 按 Tab 就縮排、按 Shift+Tab 就退縮，跨行選取一次搞定，按一次 undo 就退回去；打中文選字時 Tab 不會突然把整行推走 |
| 只用鍵盤的使用者 | 即使 Tab 被編輯區吃掉，仍有一條明確的逃脫路徑離開編輯區 |
| 後續切片的開發者 | 一個「縮排單位」物件（幾個空白／真實 tab、退縮怎麼對齊層級），以及一條把設定接進編輯器的既有路徑 |

## 3. 成功的樣子（可觀察的行為）

1. 游標在一行的任何位置按 Tab，**那一行**往右縮一級；游標與文字的相對位置不變。
2. 按 Shift+Tab，那一行往左退一級；行首空白數不是整數倍時，退到**最近的下一個層級**（3 空白 → 2 空白，不是 1 空白）。
3. 已經在最外層（行首沒有空白）時按 Shift+Tab，**什麼都不發生**：不刪字、不動游標、undo 歷史裡也不多一步。
4. 選取跨了好幾行時，被涵蓋的**每一行**都縮排（或退縮），選取範圍還在原來的那段文字上。
5. 不論在清單項目裡、在 fenced code block 裡、或在一般段落裡，行為都一樣。
6. 按一次 Tab（就算縮了十行）在 undo 歷史裡只算**一步**。
7. Tab **不會**把焦點移到別的地方，也**不會**觸發自動完成或片段展開——編輯區裡沒有任何東西會跟 Tab 搶。
8. 先按 Esc、再按 Tab，焦點**離開編輯區**（給鍵盤使用者的逃脫路徑），而且那一次 Tab 不縮排。
9. 正在用輸入法組字時按 Tab，**不縮排**——而且焦點也不會因此跑出編輯區。
10. 縮排單位預設 2 個空白，可以換成 4 個空白或真實 tab 字元；同一份文件只用一種。

## 5. 例子（正常／邊界／例外）

以下例子的縮排單位一律是**預設的 2 個空白**，除非特別註明。`|` 代表游標，`[ ]` 代表選取範圍。

### 5.1 Tab：縮排

| # | 情境 | 之前 | 之後 |
| :--- | :--- | :--- | :--- |
| 1 | 正常：游標在行首 | `\|寫文章` | `··\|寫文章` |
| 2 | 正常：游標在文字之間 | `寫文\|章` | `··寫文\|章`（游標左右的字沒變） |
| 3 | 正常：游標在清單項目裡 | `- 第一項\|` | `··- 第一項\|`（成為子項目） |
| 4 | 正常：游標在行首空白區裡 | `··\|- 第一項` | `····\|- 第一項` |
| 5 | 正常：跨多行選取 | `[一\n二\n三]` | `··[一\n··二\n··三]`（三行都縮，選取還在那三行文字上） |
| 6 | 邊界：選取只涵蓋兩行的一部分 | `一[二\n三]四` | `··一[二\n··三]四`（兩行都縮） |
| 7 | 邊界：在 fenced code block 裡 | ` ```ts\nconst a = 1\|\n``` ` | ` ```ts\n··const a = 1\|\n``` ` |
| 8 | 邊界：空白行 | `\|`（空行） | `··\|` |
| 9 | 邊界：行首已經有 3 個空白 | `···\|字` | `·····\|字`（加一個單位，不做對齊） |
| 10 | 例外：正在組字 | `寫文章\|` + 組字中 | 不變（不縮排），而且焦點留在編輯區 |

### 5.2 Shift+Tab：退縮

| # | 情境 | 之前 | 之後 |
| :--- | :--- | :--- | :--- |
| 1 | 正常：行首 2 個空白 | `··寫文\|章` | `寫文\|章` |
| 2 | 正常：巢狀清單項目 | `··- 子項\|` | `- 子項\|`（回到外層） |
| 3 | 正常：跨多行選取 | `··[一\n··二]` | `[一\n二]` |
| 4 | 邊界：行首 3 個空白（不是整數倍） | `···字\|` | `··字\|`（退到最近的層級，不是 1 個空白） |
| 5 | 邊界：行首 5 個空白 | `·····字\|` | `····字\|` |
| 6 | 邊界：行首 1 個空白 | `·字\|` | `字\|` |
| 7 | 例外：已在最外層 | `字\|` | **完全不變**：不刪字、不動游標、不留 undo 步驟 |
| 8 | 例外：選取的行有些能退、有些已在最外層 | `··[一\n二]` | `[一\n二]`（能退的退，已在最外層的那行不動也不被破壞） |
| 9 | 例外：正在組字 | 組字中 | 不變 |

### 5.3 undo

| # | 情境 | 動作 | 期望 |
| :--- | :--- | :--- | :--- |
| 1 | 正常 | 選 3 行、按一次 Tab、按一次 undo | 三行同時退回原狀（一步，不是三步） |
| 2 | 正常 | 選 3 行、按一次 Shift+Tab、按一次 undo | 三行同時退回原狀 |
| 3 | 邊界 | 打一段字 → 在最外層按 Shift+Tab（不變）→ 按一次 undo | 退掉的是**打的那段字**（因為那次 Shift+Tab 沒有產生任何一步） |

### 5.4 焦點與其他鍵

| # | 情境 | 動作 | 期望 |
| :--- | :--- | :--- | :--- |
| 1 | 正常 | 按 Tab | 縮排，焦點留在編輯區 |
| 2 | 邊界 | 在最外層按 Shift+Tab（什麼都沒發生） | 焦點**還是**留在編輯區（沒動作不等於把按鍵交出去） |
| 3 | 正常 | 先按 Esc、再按 Tab | 焦點離開編輯區，且那一次 Tab 不縮排 |
| 4 | 邊界 | 按 Esc、再按別的鍵、然後按 Tab | Tab 恢復縮排（逃脫路徑只在 Esc 之後那一小段時間有效） |
| 5 | 例外 | 在一個已經打了半個詞的位置按 Tab | 只縮排。不展開片段、不跳出自動完成 |

### 5.5 縮排單位

| # | 情境 | 設定 | 動作 | 期望 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | 正常 | 預設 | Tab | 插入 2 個空白 |
| 2 | 正常 | 4 空白 | Tab | 插入 4 個空白 |
| 3 | 正常 | 真實 tab | Tab | 插入 1 個 tab 字元 |
| 4 | 邊界 | 4 空白 | 行首 6 空白按 Shift+Tab | 退到 4 空白 |
| 5 | 邊界 | 真實 tab（寬度 4） | 行首是 6 個空白的一行按 Shift+Tab | 退到 4 欄，並以 1 個 tab 字元表示（同一份文件只用一種） |

## 6. 這個切片跟輸入法的關係

需求文件 §6 是橫切約束，本切片踩到其中三條：

- **FR-8.7／FR-7.6**：組字中的 Tab 一律優先交給輸入法。共用的組字狀態（`CompositionState`）由地基切片提供，本切片**讀它**，不另外做一套。
- **FR-8.1**：組字中不得修改文件內容。不縮排就是不修改。
- **FR-8.3**：一次組字 = 一步 undo。本切片不改動歷史機制，但「一次 Tab = 一步」與它同源，一起在 T-5 驗。

人工回歸清單受影響的項目：

| 項目 | 影響 |
| :--- | :--- |
| **T-7**（組字中按 Tab） | 地基切片時是「基準值」（那時沒綁 Tab）。本切片交付後**這一項才是真正的驗收**：組字中按 Tab 必須不縮排、焦點不跑掉 |
| **T-5**（選完字後按 Cmd+Z） | Tab 現在也會寫進 undo 歷史。要確認「一次 Tab = 一步」沒有污染「一次組字 = 一步」 |

兩項都是人工，理由與地基切片一致：合成的組字事件不會叫出真的輸入法。

## 7. 假設（需求文件留白處，本切片自行裁決）

| # | 空白 | 裁決 | 理由 |
| :--- | :--- | :--- | :--- |
| A-1 | Tab 縮排時，行首空白**不是**整數倍的行要不要先對齊（3 空白 → 4 還是 → 5） | **不對齊，直接加一個單位**（3 → 5） | FR-7.4 只對「退縮」規定了對齊到最近層級，對縮排刻意沒有規定。加一個單位不改寫既有空白，副作用最小；退縮那一側自然會把它收回層級 |
| A-2 | 空白行按 Tab 要不要縮排 | **要** | 最常見的用途正是「在空行上先縮排、再開始寫子項目」。不縮排會讓使用者無法用 Tab 建立縮排的新行 |
| A-3 | 選取的行裡有些已在最外層，Shift+Tab 要整批放棄還是能退的退 | **能退的退** | §5.1 的「無動作」是針對**那一行**，不是針對整批。整批放棄會讓「選一整段退一級」在段落頂行剛好在最外層時整批失效 |
| A-4 | 組字中按 Tab，要不要順手把「焦點不要跑掉」也一併擋住（即攔下按鍵但不縮排） | **要攔**：不縮排，但那一次按鍵留在編輯區 | **這一條在 code review 中被推翻，這裡記錄修正後的裁決與原本錯在哪。**<br>原本裁決是「完全不處理，交給輸入法」，兩個理由都不成立：<br>（1）**輸入法在按鍵事件的上游。** 一個 Tab 若被輸入法拿去翻候選頁，這次按鍵根本不會抵達 App；會抵達 App 的 Tab 就是輸入法**已經放掉**的那一個。攔下它沒有從輸入法手上搶走任何東西，只取消了**預設的**焦點移動。「交給輸入法」與「不要讓焦點被搬走」從來不衝突。<br>（2）**「只攔得到組字第一瞬間」有解。** 攔截必須排在編輯器自己的按鍵處理**之前**，才能蓋住整段組字期間，而不只是組字剛開始的那一下。<br>而且這不只是無障礙問題：組字中失焦正是需求文件 §7.4 講的陷阱——組字結束事件可能永遠不來，編輯器卡在組字狀態、吃掉已經選好的字，那是 FR-8.1 的地盤 |
| A-5 | 退縮時，行首的既有空白與設定的樣式不同（例如行首是 tab、設定是空白） | **只重寫被退縮的那一行的行首空白**，用設定的樣式表示退縮後的欄數 | 那一行的行首空白本來就要改；順手統一它的樣式是 FR-7.3「同一份文件只用一種」的最小代價做法。不掃全文、不動沒被按到的行 |
| A-6 | 縮排單位的設定值目前從哪來 | 由編輯區的**呼叫端傳入**，預設 2 個空白；真正從 `settings.json` 讀出來由 vault 切片接上 | 讀設定檔屬於 vault 切片，本切片不搶。留一個具名的入口比留一個 TODO 有用 |
| A-7 | 設定裡出現不合理的寬度（0、負數、23、小數） | 建構縮排單位時**正規化**：不是 1~8 的整數就退回預設 2 | 專案慣例是「建構子內做正規化 / clamp，不信任外部值」。設定檔是使用者可以手改的檔案 |
| A-8 | 逃脫路徑要用什麼鍵、離開後停在哪 | **Esc 之後那一次 Tab 交給預設的焦點移動處理**，由外殼決定下一個焦點 | FR-7.7 明寫 Esc 後再按 Tab。焦點順序是外殼與版面的事，本切片不指定 |
| A-9 | 交付計畫與地基切片文件對本切片的 wave 標示不一致（Wave 1 / Wave 2） | 以交付計畫的 **Wave 1** 為準 | 交付計畫是切片邊界的權威，且它記錄了波次順序的修正；地基切片 BRIEF 的「Wave 2」是修正前的舊值 |

## 8. 已知不做、但要記錄的取捨

- **「焦點真的移出編輯區」沒有自動化測試。** 自動化測得到的是「那一次 Tab 沒有被編輯區攔下來」（焦點因此可以走），測不到焦點實際被放到哪——無頭環境沒有焦點順序。真正的驗收在人工步驟。
- **組字中的行為只驗得到 App 內部的判斷。** 合成的組字事件不會叫出輸入法；T-7 仍是人工。焦點那一面已經在真正建置出來的 App 上量過（組字中按 Tab／Shift+Tab，焦點留在編輯區），但送的是模擬的按鍵，不是真的注音。
- **縮排不做 Markdown 語意理解。** 清單項目縮排一級之後是不是「合法的子項目」由 Markdown 規則決定，本切片只負責行首空白。需求文件 §5.1 的括號「成為子項目」是縮排的結果描述，不是一條額外的功能。
