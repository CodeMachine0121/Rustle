# 需求共識 — Metadata 編輯與破壞性操作

- **切片**：Wave 4, `feature/metadata-editing-and-destructive-operations`
- **日期**：2026-08-20
- **輸入**：需求文件 §4.2（FR-1.5）、§4.3（FR-2.6、FR-2.7）、§3.2（R-8）、§3.4（R-18）、§8（NFR-4）、§6.2（FR-8.6／FR-8.7）、§6.3（T-9）、§7.3 分層與安全基線
- **狀態**：需求已定案（v0.3），本階段不回頭問使用者。文件留白處由本檔 §7「假設」一次裁決，並同步寫進 PR 說明

## 1. 這個切片要解決的問題

前七個切片把「寫」做完了：掃得到 vault、列得出文章、剝得掉 front matter、存得回磁碟、建得出新文章、看得到預覽。**但東西進來了就出不去，也改不了。**

- 建立文章時填錯標題、少填一個分類——目前唯一的補救方式是**在編輯區改 YAML**，而編輯區永遠看不到 YAML（FR-4.1）。也就是說：改不了。
- 寫壞的文章、名字取錯的 workspace——目前唯一的補救方式是離開 App 去 Finder。

這個切片補上三件事，而它們共用同一條紅線：**破壞性操作一律走系統垃圾桶，永不永久刪除**（NFR-4）。

```
   欄 1 的一列                       欄 2 的一列
 ┌────────────────────┐          ┌──────────────────────────┐
 │ Blog        12 篇  │          │ Tauri 與 Electron 的取捨  │
 │  [重新命名] [刪除] │          │  [編輯 metadata] [刪除]   │
 └────────────────────┘          └──────────────────────────┘
        │        │                        │           │
        │        │                        │           └─▶ 二次確認 → 系統垃圾桶
        │        │                        │               （圖片一張都不動）
        │        │                        └─▶ 同一個 GUI 表單，
        │        │                             created_at／updated_at 唯讀
        │        └─▶ 二次確認：「將刪除 N 篇文章與 M 張圖片」
        │             → 整個資料夾進系統垃圾桶
        └─▶ 就地改名（重名／保留名稱／路徑分隔字元一律擋下）
```

**真正困難的地方有三個，都不在畫面上。**

第一個是**數字必須是真的**。FR-1.5 明文要求確認訊息說出「將刪除 N 篇文章與 M 張圖片」。一個破壞性確認上的錯誤數字比沒有數字更糟——它會讓使用者根據假資訊按下不可逆的按鈕。所以數字不能取自欄 1 那一列可能已經過期的篇數，必須在**顯示確認的那一刻**去磁碟數。

第二個是**編輯器正指著要被動的那個檔案**。刪掉正在編輯的文章、重新命名正在編輯的那篇文章所在的 workspace——如果不先讓自動儲存把未存的段落寫出去、並且讓它停止指向舊路徑，結果就是「畫面顯示 A、儲存機制寫到 B」。自動儲存切片已經把這件事的出入口做成兩道會**拒絕**的門（`openArticle`／`closeArticle`），本切片一律走那兩道門，拒絕就什麼都不動。

第三個是**改 metadata 不能動到檔案裡的其他任何東西**。使用者自己加的 `draft: true`、手寫的註解、鍵的順序、CRLF、BOM——front matter 切片的寫入路徑已經逐位元保住這些（R-8），本切片**不另寫第二個序列化器**，只指名 `title`／`category`／`tags`／`updated_at` 四個欄位。

## 2. 對誰有價值

| 角色 | 拿到什麼 |
| :--- | :--- |
| 寫作者 | 事後改得動標題、分類、標籤，而且不必看見一行 YAML |
| 寫作者 | 刪得掉寫壞的文章與取錯名字的 workspace，不必離開 App |
| 手滑的寫作者 | 刪除一律進系統垃圾桶，Finder 裡按一下就回得來 |
| 貼過圖的寫作者 | 刪文章不會順手刪掉別篇也在用的圖（R-18） |
| 要按下不可逆按鈕的寫作者 | 確認訊息上的數字是這一刻去磁碟數出來的，不是畫面上快取的 |
| 正在編輯的寫作者 | 破壞性操作前未存的段落一定先落磁碟；落不了就整件事不發生，而且說得出為什麼 |
| 寫中文的寫作者 | 新增的每一個輸入欄位（metadata 表單三欄、重新命名一欄）的 `Enter` 都屬於輸入法 |
| 所有人 | 「建立文章失敗」不再假扮成「讀不到這個 workspace」——破壞性與建立類操作有了一個真正的錯誤出口 |

## 3. 成功的樣子（可觀察的行為）

1. 欄 2 每一列有「編輯 metadata」，點開的表單與建立文章對話框同形：Title 一行、Category 與 Tags 是 chip，候選來自這個 workspace 既有的詞。
2. 表單開啟時三個欄位**已經填好這篇文章現在的值**。
3. 建立時間與更新時間**以文字顯示、沒有任何可填欄位**，畫面上說得出它們由 Rustle 自己維護。
4. 儲存之後：檔案裡只有 `title`／`category`／`tags`／`updated_at` 變了；`created_at`、未知欄位、註解、鍵順序、行尾與 BOM 一個位元都沒動；正文一個位元都沒動。
5. 儲存之後欄 2 那一列跟著更新（新標題、新分類、新的更新時間）。
6. 改的是正在編輯的那一篇時：未存的段落先被寫出去，改完之後編輯器仍然開著同一篇，而且**不會**跳出「檔案被外部改動」的警示——那個寫入是我們自己做的。
7. 欄 2 每一列有「刪除」，按下去先出現二次確認，說明「移到系統垃圾桶」與「圖片不會被刪除」。
8. 確認之後：`.md` 檔進系統垃圾桶（不是永久刪除），`images/` 一張圖都不少，欄 2 那一列消失，欄 1 的篇數跟著減一。
9. 刪掉的是正在編輯的那一篇時：編輯區清空、欄 2 沒有任何一列被選取。
10. 欄 1 每一列有「重新命名」與「刪除」。
11. 重新命名：輸入新名稱按 `Enter`，資料夾就地改名；空白、含 `/` 或 `\`、`images`、以 `.` 開頭、已經有人用了——一律擋下並說出原因，資料夾不動。
12. 重新命名的是正在使用的那個 workspace 時：改完之後它仍然是被選取的那一個（用新名字），文章清單照樣列得出來。
13. 刪除 workspace 的確認訊息說出「將刪除 N 篇文章與 M 張圖片」，而 N 與 M 是**這一刻**去磁碟數出來的。
14. 確認之後整個 workspace 資料夾進系統垃圾桶，欄 1 少一列。
15. 任何一項操作失敗（磁碟滿、權限不足、未存變更還沒處理完），畫面上出現一則**專屬於這次操作**的提示，說得出是哪一個操作、為什麼失敗，而且可以關掉。它不再借用欄 2 的「讀不到這個 workspace：」。
16. 組字中按 `Enter`：不送出表單、不建立 chip；組字中按 `Esc`：對話框不關。

## 4. 邊界：本切片明確不做

| 不做 | 為什麼 |
| :--- | :--- |
| **刪除文章時清理圖片** | R-18 明文禁止。`images/` 是 workspace 共用，同一張圖可能被多篇引用，誤刪的代價遠高於孤兒檔案 |
| **重新命名文章檔案** | R-9：改標題不動檔名。「重新命名檔案」是需求文件裡另一個明確的動作，沒有指派給任何切片 |
| **編輯 `created_at`／`updated_at`** | FR-2.7 明文唯讀 |
| **在編輯區改 YAML** | FR-4.1 硬性需求 |
| **多選刪除、批次操作** | 需求沒有。破壞性操作一次一個，確認訊息才說得準 |
| **復原（undo）刪除** | 系統垃圾桶就是復原路徑（NFR-4 的選擇），App 內不另做一套 |
| **搬移文章到另一個 workspace** | 需求沒有 |
| **清單篩選、排序、分隔線、捲動同步** | 另一條切片（`feature/list-controls-and-preview-geometry`） |
| **貼上圖片** | 另一條切片（`feature/paste-image-to-workspace`） |
| **硬連結（hard link）的範圍檢查** | 發佈檢查清單 S-3，明文「這個方法解不了」。本切片不宣稱關掉它 |

## 5. 用例子把邊界釘死

### 5.1 改 metadata 到底改了檔案裡的什麼

原檔（使用者自己加了 `draft`，還寫了一行註解）：

```markdown
---
# 這一行是使用者自己寫的註解
title: 舊標題
draft: true
created_at: 2026-08-20T14:32:05+08:00
updated_at: 2026-08-20T16:04:11+08:00
tags:
  - electron
---

正文第一行。
```

把標題改成「新標題」、加一個分類「技術筆記」之後：

| 檔案裡的東西 | 結果 |
| :--- | :--- |
| `title` | 變成「新標題」 |
| `category` | 新增，YAML list 形式（R-6），即使只有一個元素 |
| `tags` | 沒動它就不動（送出的值與現況相同時也一樣是原樣） |
| `updated_at` | 變成儲存那一刻的時間 |
| `created_at` | **不動** |
| `draft: true` | **不動**（R-8 的未知欄位） |
| 那一行註解 | **不動**，位置也不變 |
| 鍵的順序 | **不動**（`title` 仍在 `draft` 之前，`category` 加在末尾） |
| 正文 | **不動**，逐位元相同 |
| CRLF／BOM | 檔案本來是什麼就還是什麼 |

### 5.2 標題與空值

| 送出的值 | 結果 |
| :--- | :--- |
| 標題「　新標題　」 | 寫進去的是「新標題」（前後空白修掉） |
| 標題全是空白 | 「儲存」是停用的；負責檔案存取的那一層也不信任畫面層，硬送一律拒絕，檔案一個位元不動 |
| 分類 `["技術筆記", "技術筆記"]` | 寫進去一個（去重，保留第一次出現的順序） |
| 分類 `["技術筆記", "技術"]` | 兩個都寫（大小寫／不同寫法是使用者自己的選擇，不幫他合併） |
| 分類全部被移除 | 檔案裡的 `category` 這個鍵**消失**（沒有內容的鍵沒有話要說） |
| chip 欄位裡還有沒變成 chip 的字就按儲存 | 那個字也一起收成 chip（與建立文章對話框同一條規則） |

### 5.3 刪除文章

| 情況 | 結果 |
| :--- | :--- |
| 按「刪除」 | 先出現二次確認，說明會移到系統垃圾桶、圖片不會被刪 |
| 確認 | `.md` 進系統垃圾桶；`images/` 底下一個檔案都沒少 |
| 取消／按 `Esc` | 什麼都不發生 |
| 刪的是正在編輯的那一篇 | 未存的段落**先寫出去**（所以垃圾桶裡的那份是最新的），然後編輯區清空 |
| 刪的是正在編輯的那一篇，但外部改動警示還沒被回答 | **什麼都不刪**，畫面上說出「先回答標題列的提示」 |
| 刪的是正在編輯的那一篇，但上一次寫檔失敗 | 第一次拒絕並說明；**再按一次就放掉未存的變更並刪除**（與切換文章同一條規則：會毀掉東西的動作要有第二次、知情的嘗試） |
| 刪的是別的一篇 | 編輯區與選取完全不動 |

### 5.4 刪除 workspace 的數字

`Blog/` 底下有 `a.md`、`b.md`、`README.txt`、`images/`（`1.png`、`2.png`、`.DS_Store`）。

| 確認訊息說什麼 | 為什麼 |
| :--- | :--- |
| 「將刪除 **2** 篇文章與 **2** 張圖片」 | 文章＝第一層的 `.md`（R-3、R-5）；圖片＝`images/` 底下不是資料夾、也不是以 `.` 開頭的檔案 |
| 另外一句：「整個 `Blog` 資料夾會移到系統垃圾桶」 | `README.txt` 也會跟著走。只報兩個數字會漏講這件事，而確認訊息不該漏講 |

`.DS_Store` 不算一張圖片：macOS 幾乎每個被 Finder 開過的資料夾都有它，把它算進去等於**每次都多報一張**，那就是「錯的數字」。

### 5.5 重新命名 workspace

| 新名稱 | 結果 |
| :--- | :--- |
| `Writing` | 資料夾就地改名為 `Writing` |
| 空白 | 擋下：「請先輸入 workspace 名稱。」 |
| `a/b`、`a\b` | 擋下：一個 workspace 就是一層資料夾 |
| `images`、`.hidden` | 擋下：保留名稱 |
| `Work`（已經有一個 `Work`） | 擋下：這個名稱已經有人用了 |
| `blog`（原本就叫 `Blog`） | 擋下（比對不分大小寫，因為檔案系統也不分）。**只改大小寫目前做不到**，見 §7 A-8 |
| 改的是正在使用的那個 workspace，而且有一篇文章開著 | 未存的段落先寫進**舊路徑**（改名前），然後編輯區清空，改名後那個 workspace 仍然被選取（新名字），文章清單重新列出 |
| 改的是正在使用的那個，但外部改動警示還沒被回答 | **不改名**，畫面上說出原因 |

### 5.6 錯誤出口（本切片被指派的既有問題）

現在欄 2 只有一句話可以說：「讀不到這個 workspace：{原因}」。而「建立文章時撞名」走的也是這句話——那是在說謊：撞名不是讀不到。本切片建立一個**與操作綁定**的提示：

| 操作 | 提示長什麼樣 |
| :--- | :--- |
| 建立文章失敗 | 「建立文章失敗：{負責檔案存取的那一層的原話}」 |
| 更新 metadata 失敗 | 「更新 metadata 失敗：{負責檔案存取的那一層的原話}」 |
| 刪除文章失敗 | 「刪除文章失敗：{負責檔案存取的那一層的原話}」 |
| 重新命名 workspace 失敗 | 「重新命名 workspace 失敗：{負責檔案存取的那一層的原話}」 |
| 刪除 workspace 失敗 | 「刪除 workspace 失敗：{負責檔案存取的那一層的原話}」 |
| 未存變更還沒處理完（外部改動警示） | 「…：請先回答標題列的外部改動提示，再試一次。」 |
| 上一次寫檔失敗 | 「…：上一次儲存失敗。再按一次就會放掉未儲存的變更並繼續。」 |

提示可以關掉，而且**下一次操作成功就自己消失**——一則留在畫面上的舊錯誤會讓人以為剛剛那次也失敗了。

## 6. 不在本切片但要留好接縫

| 接縫 | 給誰 |
| :--- | :--- |
| 「把某個 vault 裡的東西移到系統垃圾桶」這個能力（以名稱指定，不以路徑） | 任何之後需要刪東西的切片（清理孤兒圖片、刪除設定） |
| 「這次操作失敗了」這個畫面出口 | 任何之後有非致命失敗要說的切片，不必再借用某一欄的讀取失敗 |
| 「動檔案之前先讓自動儲存讓路」這道門 | 任何之後會從畫面層改動正在編輯的那個檔案的切片 |
| 「一個 workspace 裡有幾篇文章、幾張圖片」這個算法 | 之後若要顯示 workspace 大小、或做孤兒圖片清理 |

## 7. 假設（需求文件沒寫，本切片一次裁決）

| # | 假設 | 為什麼這樣選 |
| :--- | :--- | :--- |
| A-1 | **入口放在每一列上**：欄 2 每列「編輯 metadata」「刪除」，欄 1 每列「重新命名」「刪除」 | 需求只說「可刪除／可重新命名」。放在列上，操作的對象不會被誤認；不做右鍵選單，因為那對鍵盤使用者是死路 |
| A-2 | 刪除確認、重新命名都是**畫面內的對話框／欄位**，不用系統原生 dialog | 原生 dialog 不經過具名通道，會把「畫面層只透過具名通道說話」這件事變成兩套路徑；而且原生 dialog 測不到 |
| A-3 | 刪除的確認**焦點預設落在「取消」** | 破壞性操作。焦點在確認鈕上時一次 `Enter` 就不可逆了，而 `Enter` 正好是輸入法的確定鍵 |
| A-4 | 確認對話框**不綁 `Enter` 為確認**；`Esc` 取消 | 同上。確認只能點，或把焦點移到確認鈕再按（那是按鈕本身的鍵盤啟動，不是隱性送出） |
| A-5 | 「將刪除 N 篇文章與 M 張圖片」的數字在**顯示確認的那一刻**去磁碟數；刪除時再數一次，回報真的走掉多少 | FR-1.5 的數字是使用者按下不可逆按鈕的依據。欄 1 那一列的篇數是上一次列表的結果，可能已經過期 |
| A-6 | 圖片＝`images/` 底下**不是資料夾、名稱不以 `.` 開頭**的檔案 | 見 §5.4。`images/` 底下的子資料夾（罕見）不逐層數，它們會跟著整個資料夾一起進垃圾桶——確認訊息裡那句「整個資料夾會移到系統垃圾桶」把這件事講完了 |
| A-7 | 改 metadata 用**讀出檔案當下的修改時間當作寫入的預期值**（先讀後寫），而不要求畫面層帶著預期值 | 清單那一列不帶檔案修改時間，加上去會讓每一列都背一個只有這個操作用得到的欄位。先讀後寫的窗口是兩個 syscall 寬，與自動儲存的原子寫檔同一個等級 |
| A-8 | 只改大小寫的重新命名（`Blog` → `blog`）**擋下** | 撞名比對不分大小寫，因為檔案系統不分。在不分大小寫的檔案系統上「改大小寫」需要先改成第三個名字再改回來，那是一條需求，現在沒有 |
| A-9 | 改**正在編輯的那一篇**的 metadata 時，順序是：先讓自動儲存把正文寫出去（可被拒絕）→ 寫 metadata → 用新的檔案修改時間重新開啟同一篇 | 不這樣做，我們自己的寫入會被自動儲存誤判為「外部改動」，而那個警示會要使用者在自己剛剛做的事上二選一 |
| A-10 | 破壞性操作**先儲存再刪**（走既有的那道門） | 垃圾桶裡的那份是最新的，救回來的價值最高。而且「刪之前不儲存」需要一條專屬規則，App 目前只有一條「離開前先寫」的規則，多一條就是多一種行為 |
| A-11 | 刪掉正在編輯的那一篇之後，**不自動打開別的一篇** | 自動選一篇等於幫使用者決定接下來寫什麼，而且它下一步可能又刪掉那一篇。空的編輯區有空狀態在說話（FR-4.8） |
| A-12 | 刪掉正在使用的 workspace 之後，**不自動選另一個 workspace** | 同上 |
| A-13 | 重新命名正在使用的 workspace 之後，**它仍然被選取（新名字），但編輯區清空** | 「換 workspace 就清空編輯區」是 vault 切片已經定的行為；改名走的是同一條路（必須先關掉文章才能動資料夾），沿用同一個結果比多一種行為好 |
| A-14 | 更新 metadata 成功後**重讀整個文章清單**，不在畫面層改那一列 | 與建立文章同一個理由：排序與欄位形狀的規則住在負責檔案存取的那一層 |
| A-15 | 讀取確認數字失敗時**不開啟確認對話框**，直接走錯誤提示 | 一個沒有數字的破壞性確認就是 FR-1.5 要避免的東西 |
| A-16 | 更新 metadata 時若檔案剛剛被別的程式改過（先讀後寫之間），**一律拒絕、什麼都不寫**，並告訴使用者可以再試 | 這條路徑沒有「覆寫／重新載入」兩個選擇可以問——那是自動儲存對正文的規則。metadata 的正確答案是不要蓋掉別人的修改 |
