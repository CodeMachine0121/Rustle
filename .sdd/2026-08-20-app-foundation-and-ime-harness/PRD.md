## 1. 目標

讓 Rustle 從「只有需求文件」變成「打得開、打得字、邊界已經畫死、後面十條分支不會互撞」。

## 2. User Stories

| ID | 故事 |
| :--- | :--- |
| **US-1** | 作為每天用中文寫文章的使用者，我要有一個能打開的視窗與一塊能打中文的 Markdown 編輯區，這樣輸入法有問題時我第一週就知道，而不是功能全做完才發現 |
| **US-2** | 作為使用者，我要編輯區的長行自動折行、Markdown 語法有高亮，這樣我在折行處打中文時的風險能被真實地驗到 |
| **US-3** | 作為使用者，我要 App 只在我的 vault 範圍內讀寫檔案，指向 vault 外面的一律拒絕，這樣一個寫壞的功能不會動到我 vault 以外的東西 |
| **US-4** | 作為使用者，我要畫面層不能直接碰檔案系統、不能載入任何外部資源，這樣我貼進來的 Markdown 不可能在 App 內執行程式碼或把內容送出去 |
| **US-5** | 作為後續切片的開發者，我要一份一次定義齊全的通道清單，這樣我實作自己那一支時不需要動任何共用檔案 |
| **US-6** | 作為後續切片的開發者，我要一個「組字中會暫停倒數」的共用零件，這樣自動儲存與預覽重繪不必各自重新發明，也不會各自漏掉組字狀態 |
| **US-7** | 作為使用者，我要一份寫清楚每一項期望結果的輸入法回歸清單留在專案裡，並且明訂升級所用的 GUI 框架或編輯器元件前必須重跑 |

## 3. 業務流程

### 3.1 啟動

```
使用者執行啟動指令
   → App 建立視窗（畫面層不具備檔案系統能力，與負責檔案存取的那一層隔離）
   → 畫面層載入的每一份內容都套用內容安全政策
   → 負責檔案存取的那一層把通道清單上的每一個項目各自綁到它的處理器
   → 畫面層載入，通道清單上的具名方法是它對負責檔案存取的那一層的唯一入口
   → 畫面層顯示 Markdown 編輯區，載入記憶體中的示範正文
   → 使用者可以開始打字
```

### 3.2 一次通道呼叫

```
畫面層呼叫具名方法（帶結構化名稱，不帶路徑）
   → 負責檔案存取的那一層找到該通道的處理器
   → 處理器需要位置時，向路徑範圍檢查要（唯一取得絕對路徑的途徑）
        ├─ 落在 vault 內 → 回傳絕對路徑，繼續
        └─ 落在 vault 外或名稱不合法 → 拋出「逃出 vault」錯誤，不做任何讀寫
   → 尚未由任何切片實作的通道 → 拋出「尚未實作」錯誤，錯誤訊息帶出通道名
```

### 3.3 組字中暫停倒數

```
畫面層排一件延遲工作（自動儲存 1 秒 / 預覽重繪 150 毫秒）
   → 倒數中收到「組字開始」 → 記住剩餘時間，停止倒數
   → 組字期間再排新工作 → 只記下來，不開始倒數
   → 收到「組字結束」 → 從剩餘時間接著倒數
   → 倒數走完 → 執行工作
```

### Feature：每個通道都回答「成功」或「結構化的失敗」

```gherkin
場景: 丟出來的東西根本不是錯誤時也要說得出話
  當 處理過程丟出一個沒有訊息的東西
  那麼 結果仍是失敗、原因為 unexpected，訊息說明負責檔案存取的那一層沒有交代原因
```

### Feature：自訂 protocol 的註冊接縫

> 本節於 code review 後追加。`rustle:` 已保留在內容安全政策裡，但註冊 protocol 是 App 層級的動作、只能從組裝根進行，而組裝根被列為「沒有人可以改」——預覽切片沒有接縫可用。

```gherkin
# TC-42
場景: 服務 vault 資產的 scheme 已宣告齊全
  當 建立 protocol 註冊表
  那麼 只登記一個 scheme，即服務 vault 資產的那一個

# TC-43
場景: 每個 scheme 的權限在 App 就緒前宣告
  當 詢問註冊表要宣告的 scheme 權限
  那麼 得到該 scheme 的權限宣告（視為標準來源、視為安全來源、支援串流）

# TC-44
場景: 沒有任何 scheme 可以繞過內容安全政策
  當 檢視所有 scheme 的權限
  那麼 沒有任何一個宣告可以忽略內容安全政策
  並且 沒有任何一個宣告內容安全政策目前擋得死的權限（例如在 `connect-src 'none'` 之下宣告 fetch 支援）

# TC-45
場景: 兩個處理器搶同一個 scheme 在組裝時就被擋下
  假設 兩個處理器都宣告服務同一個 scheme
  當 建立註冊表
  那麼 組裝失敗並指出重複的 scheme

# TC-46
場景: 尚未實作的 scheme 被請求時明確報錯
  當 請求服務 vault 資產的 scheme
  那麼 明確回報該 scheme 尚未實作，訊息看得到 scheme 名稱
```

### Feature：編輯區把組字狀態告訴其他人

> 本節於 code review 後追加。原本編輯區是以參數取得組字狀態，而共用情境那條路徑零消費者零測試；同一個物件有兩條取得路徑，正是「總有一天有人會忘記」的來源。

```gherkin
# TC-47
場景: 編輯區開啟時顯示交給它的正文
  當 編輯區掛載
  那麼 編輯區內容包含傳入的正文，且可編輯

# TC-48
場景: 組字開始時，共用的組字狀態變成組字中
  假設 編輯區已掛載在一個組字狀態之下
  當 編輯區收到組字開始
  那麼 該組字狀態為組字中

# TC-49
場景: 組字結束時，共用的組字狀態不再是組字中
  當 編輯區收到組字開始，接著收到組字結束
  那麼 該組字狀態不再是組字中

# TC-50
場景: 編輯區不需要別人把組字狀態當屬性交給它
  當 編輯區掛載在一個組字狀態之下並經歷一次完整組字
  那麼 該組字狀態依序收到「開始」與「結束」兩次通知

# TC-51
場景: 沒有提供組字狀態時，編輯區拒絕掛載
  當 在沒有組字狀態的地方掛載編輯區
  那麼 明確報錯，而不是安靜地不感知組字
```
