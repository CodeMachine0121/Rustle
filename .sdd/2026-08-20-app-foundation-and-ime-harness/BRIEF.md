# 需求共識 — 地基與輸入法回歸測試骨架

- **切片**：Wave 0，`feature/app-foundation-and-ime-harness`
- **日期**：2026-08-20
- **輸入**：需求文件 §6、§7、§11-1、NFR-7
- **狀態**：需求已定案（v0.3），本階段不回頭問使用者；文件留下的空白由本檔的「假設」一節裁決

---

## 1. 這個切片要解決的問題

Rustle 現在只有需求文件，沒有可以打開的東西。在能談任何一個功能之前，得先有一個**真的會啟動、真的能打字的 App**，而且它一開始就長在正確的骨架上——否則後面每一條需求都會踩在錯的地基上。

因此本切片解決三件事：

1. **能打字給人看。** 有一個真的視窗、真的 Markdown 編輯區，讓「用注音打一整段中文」這件事今天就能被人親手驗證，而不是等功能全做完才發現輸入法有問題。
2. **安全的邊界一次立好。** Rustle 會把使用者的 Markdown 渲染成 HTML、會讀寫使用者的檔案。這兩件事天生危險，邊界必須在第一天就畫死，而不是事後補。
3. **後面十條分支不互撞。** 十一個功能切片會平行開發，它們共用同一份「畫面與檔案之間的對話清單」。這份清單今天一次定義齊全，之後每個切片只補自己那一支，不需要回頭動共用的部分。

## 2. 對誰有價值

| 角色 | 拿到什麼 |
| :--- | :--- |
| 使用者（James，每天用中文寫文章） | 一個可以開起來、可以打中文的編輯區，以及一份可以照著跑的輸入法檢查清單——輸入法有問題會在第一週被發現，不是第一年 |
| 後續切片的開發者（同一個人／AI） | 一份已經定案的分層地圖、一份已經定義齊全的通道清單、一組已經寫好的「組字中要暫停」的共用零件 |

## 3. 成功的樣子（可觀察的行為）

1. 執行一個指令，Rustle 的視窗會打開，中間有一塊 Markdown 編輯區，裡面已經有一段示範正文。
2. 那塊編輯區看得到 Markdown 語法高亮；很長的一行會**自動折到下一行**，不會出現橫向捲軸。
3. 在那塊編輯區可以用注音打中文；能不能打對，照著專案內的檢查清單一項一項驗。
4. 畫面那一側**碰不到任何檔案**：它沒有讀寫檔案的能力，只能透過一份具名清單向後面那一側要資料。
5. 後面那一側收到任何「哪個 workspace、哪篇文章、哪張圖」的指定時，會先確認它落在 vault 裡面；指向 vault 外面的一律拒絕，不做任何讀寫。
6. 清單上每一個項目都有人接。這個切片不負責實作的項目，被呼叫時會明確回答「這個還沒實作」，而不是安靜地什麼都不做或整個崩掉。
7. 專案內留著一份輸入法回歸清單（12 項，每項寫清楚期望結果），以及一份發佈檢查清單，明講「升級所用的 GUI 框架或編輯器元件之前必須重跑」。
8. 共用的「組字中要暫停」零件會真的暫停：計時器在組字開始時停下來，組字結束後才接著跑完剩下的時間。

## 4. 邊界：本切片明確不做

需求文件裡屬於別人的部分，這裡一律不碰——碰了就是搶別人的檔案，平行開發一定撞車。

| 不做 | 誰做 |
| :--- | :--- |
| 掃 vault、列 workspace、列文章 | Wave 1 `vault-workspace-and-article-listing` |
| Front matter 剝離／接回、真的讀檔案內容 | Wave 1 `front-matter-and-body-loading` |
| Tab / Shift+Tab 縮排 | Wave 2 `tab-indentation-behavior` |
| 建立文章對話框、chip 輸入 | Wave 2 `create-article-dialog` |
| 自動儲存、原子寫檔、外部改動偵測 | Wave 2 `autosave-and-atomic-write` |
| 預覽面板、Markdown 渲染與淨化 | Wave 3 `preview-panel` |
| 貼上圖片、圖片落檔、自訂 protocol 的註冊 | Wave 3 `paste-image-to-workspace` |
| 四區塊版面（workspace 欄、文章欄、預覽欄） | Wave 1 / Wave 3 |
| 設定檔的實際讀寫 | Wave 1（`settings*` 屬於 vault 切片） |

**編輯區這一塊也刻意留白**：不綁 Tab、不接自動儲存、不接預覽、不接貼圖、不做多游標之外的花樣。它現在的唯一任務是「能打中文、看得到語法、會折行」。

## 5. 輸入法：這一節的處理方式（重要決定）

需求文件 §6.3 的 T-1 ~ T-12 是**人工執行的檢查清單**，不是自動化測試。

理由是誠實的：那 12 項要驗的是「真實輸入法（含 macOS 內建注音／拼音與第三方）在真實候選視窗下的行為」。用程式驅動的合成組字事件走的是渲染引擎的組字路徑，**不會叫出任何一個真的輸入法、也不會畫出候選視窗**——而 T-2、T-3、T-8 要驗的正是「候選視窗貼齊游標」。一個不叫出輸入法就綠燈的測試，比一條寫清楚的人工步驟更糟：它會讓人以為這件事被守住了。

因此：

- T-1 ~ T-12 **一律人工**，以 runbook 形式留在專案內，每項寫明「怎麼做、期望看到什麼、看到什麼算失敗」。**這是決定，不是遺漏。**
- 由使用者在功能大致完成後親手跑一輪；升級所用的 GUI 框架或編輯器元件之前必須重跑（寫進發佈檢查清單）。
- 自動化只做**能誠實自動化的那一段**：橫切約束裡「組字中要暫停計時」這條，是純粹的時間邏輯，不需要真的輸入法就能驗——這部分做成單元測試。

## 6. 例子（正常／邊界／例外）

### 6.1 路徑範圍檢查

| 情境 | 給的東西 | 期望 |
| :--- | :--- | :--- |
| 正常 | workspace `Blog`、文章 `zen-of-writing.md` | 得到 vault 底下對應的位置 |
| 正常 | workspace 名稱含中文 `讀書筆記` | 一樣接受，得到對應位置 |
| 邊界 | workspace `Blog`、文章 `2026-q3-review.md`（不存在的檔） | 位置照算（存不存在是讀檔那一刻的事，不是範圍檢查的事） |
| 例外 | workspace `../..` | 拒絕，不回傳任何位置 |
| 例外 | 文章 `../../../etc/passwd` | 拒絕 |
| 例外 | workspace `/etc` （絕對路徑） | 拒絕 |
| 例外 | workspace 名稱含 `/` 或 `\` | 拒絕（workspace 是資料夾名稱，不是路徑） |
| 例外 | workspace 名稱為空字串或全空白 | 拒絕 |
| 例外 | 名稱為 `.` 或 `..` | 拒絕 |
| 例外 | 圖片檔名 `../x.png` | 拒絕 |

### 6.2 通道清單

| 情境 | 動作 | 期望 |
| :--- | :--- | :--- |
| 正常 | 檢查清單完整性 | 清單上宣告的每一個項目都找得到接它的人 |
| 例外 | 呼叫本切片不負責實作的項目 | 明確得到「這個項目尚未實作」的錯誤，錯誤訊息帶得出是哪一個項目 |
| 例外 | 兩個人搶著接同一個項目 | 組裝時就擋下來，不是等到執行才發現 |
| 例外 | 呼叫清單上沒有的項目 | 找不到接的人，明確報錯 |

### 6.3 組字中暫停計時

| 情境 | 動作 | 期望 |
| :--- | :--- | :--- |
| 正常 | 排一件事、等時間到 | 事情執行 |
| 正常 | 時間還沒到又排一次 | 倒數重新開始，只執行一次 |
| 邊界 | 倒數中開始組字，然後把時間拉超過原本的期限 | **不執行**（計時暫停） |
| 邊界 | 組字結束後再等剩下的時間 | 執行（把暫停前剩下的時間走完，不是重頭數） |
| 邊界 | 組字期間排新的一件事 | 不立刻執行，等組字結束後才開始倒數 |
| 例外 | 沒有在組字時收到「組字結束」 | 不因此執行任何事、不報錯 |
| 例外 | 排完後取消 | 不執行 |

### 6.4 內容安全政策

| 情境 | 期望 |
| :--- | :--- |
| 正式版本 | 預設什麼都不准載入；程式與樣式只准來自 App 自己；圖片只准來自 App 自己、內嵌資料與 vault 專用來源；**不准對外連線** |
| 開發版本 | 可為開發工具所需而額外放寬，其餘一致 |

## 8. 已知不做、但要記錄的取捨

- **編輯區沒有自動化測試。** 編輯區的價值（打中文不出錯、折行、語法高亮）只有真人配合真輸入法才驗得準；在無頭環境自動化驗編輯器內部結構，驗到的是實作細節不是行為。因此編輯區的驗收落在 runbook，不落在測試。
- **開發版本的內容安全政策比正式版本鬆。** 開發工具可能需要額外的連線或內嵌程式；這是必要的代價，正式版本維持嚴格。
