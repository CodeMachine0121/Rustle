## 1. 這個切片要解決的問題

Rustle 的核心主張是「**寫作時眼前只有正文**」——metadata 在建立時用 GUI 設定完，之後永遠不出現在眼前。地基切片交付了一個能打字的編輯區，但它載入的是記憶體裡的示範正文；**目前沒有任何程式碼真的打開過使用者的檔案**。

一篇文章在磁碟上長這樣：

```markdown
---
title: Tauri 與 Electron 的取捨
created_at: 2026-08-20T14:32:05+08:00
updated_at: 2026-08-20T16:04:11+08:00
category:
  - 技術筆記
tags:
  - electron
---

這裡才是正文的第一行。
```

本切片要做的事，就是這個檔案與編輯區之間那條翻譯：**讀進來時把 `---` 區塊拆下來，只把正文交給編輯區；寫回去時再把（可能已更新的）區塊接回檔頭，而且接回去的東西必須跟原本一模一樣。**

「一模一樣」是這個切片真正困難的地方。使用者的 front matter 裡可能有 Rustle 不認識的欄位（`draft: true`）、有自己排的鍵順序、有寫給自己看的註解。Rustle 只被授權改動它認識的那幾個欄位；其他每一個位元都不該因為「我們存了一次檔」而改變。

## 2. 對誰有價值

| 角色 | 拿到什麼 |
| :--- | :--- |
| 使用者（James） | 點一篇文章，編輯區只看到正文，永遠看不到 `---`。存檔之後用 Obsidian／Git 打開同一個檔案，他自己加的欄位、鍵順序與註解都還在原位 |
| 使用者（把 vault 丟給 Hugo／Obsidian 的人） | 檔案脫離 Rustle 依然自我描述——因為 Rustle 從來沒有把它重寫成自己的格式 |
| Wave 2 的文章清單切片 | 一份「寬容解析」的 metadata：`category` 寫成單一字串也讀得懂，沒有 `title` 也給得出一列可以顯示的東西，並且標記出「這列的 metadata 不完整」 |
| Wave 2 的自動儲存切片 | 一個「把正文接回檔頭」的物件，它只要負責時機與原子寫檔，不必自己碰 YAML |
| Wave 3 的建立文章切片 | 一個「由標題產生檔名」的物件，含同名衝突時的編號規則 |

## 3. 成功的樣子（可觀察的行為）

1. 選一篇有 front matter 的文章，編輯區顯示的第一行是**正文**的第一行；`---` 區塊與 `title:` 那些行**完全不出現**。
2. 正文裡本來就有的 `---`（分隔線、或第二個 YAML 區塊）**不會被當成 front matter 吃掉**。
3. 一個完全沒有 front matter 的 `.md` 檔，整個檔案內容就是正文，照樣打得開。
4. 讀進來的 metadata 是寬容的：`category: 技術筆記`（單一字串）讀成一個元素的清單；沒有 `title` 的檔案，標題以**檔名（去掉 `.md`）**代替，並且這一列被標成「metadata 不完整」。
5. 存檔之後，front matter 裡：Rustle 不認識的欄位還在、鍵的順序沒變、註解還在原來的位置與行上——只有 Rustle 被要求改的那個欄位改了。
6. `category` 與 `tags` 一律寫成 YAML 清單形式，即使只有一個元素，也不會出現逗號字串。
7. 由標題產生檔名時：`Tauri 與 Electron 的取捨` 這種**非 ASCII 標題保留原字元**；空白變 `-`；檔名不合法的字元被移除；已經有同名檔案時自動變成 `-2`、`-3`。
8. 指向 vault 外面的東西一律讀不到——包含「vault 裡有一個符號連結指向外面」這種以前擋不住的情況。

## 4. 邊界：本切片明確不做

| 不做 | 誰做 |
| :--- | :--- |
| 掃 vault、列 workspace、列文章、四區塊版面 | Wave 2 `vault-workspace-and-article-listing` |
| 自動儲存的時機（停止輸入 1 秒、切換文章前先存）、原子寫檔、外部改動偵測 | Wave 2 `autosave-and-atomic-write` |
| 建立文章對話框、真的建立檔案 | Wave 3 `create-article-dialog` |
| 事後編輯 metadata 的對話框 | Wave 4 `metadata-editing-and-destructive-operations` |
| Tab／Shift+Tab 縮排、預覽面板、貼上圖片 | 各自的切片 |
| 編輯區「載入哪一篇」的 UI 互動（FR-2.3 的點選半段） | Wave 2（版面與清單）；本切片只負責「給定一篇文章 → 交出正文」 |

**特別說明兩件事**：

- **`saveBody` 這個通道不由本切片交付。** 它的 handler 仍然回答「尚未實作」。本切片交付的是**文件物件本身**——「把正文接回 front matter、只改該改的欄位」的行為與它的測試。Wave 2 的自動儲存切片負責時機、原子寫檔與外部改動偵測，屆時從它自己的 domain service 呼叫這個物件。理由：時機與原子寫檔是那個切片的需求（R-10~R-12），本切片若順手做了，兩條分支就會搶同一份寫檔邏輯。
- **由標題產生檔名（R-9）與寫入 metadata 欄位（R-6）現在沒有 in-app 呼叫者**，因為 `createArticle`／`updateMetadata` 是別人的通道。它們仍然在本切片交付，因為 R-6~R-9 是本切片覆蓋的需求，而且「檔名怎麼產生」與「欄位怎麼序列化」屬於同一個文件物件的知識，拆到別的切片會變成兩份 YAML 知識。

## 5. 為什麼不能把 YAML 解成普通物件再寫回

需求文件 §7.3 已經直接指定：**YAML 必須以保留文件結構的方式處理**，並且點名不走「解成普通物件再重新序列化」那條路——那條路**註解與鍵順序在那一刻就沒了**，直接違反 R-8。

本切片照辦。這也意味著要新增一個能保留註解與鍵順序的 YAML 依賴（見 §7 的 A-0）。

## 6. 例子（正常／邊界／例外）

### 6.1 剝離 front matter（FR-4.1）

| 情境 | 檔案內容 | 期望交給編輯區的正文 |
| :--- | :--- | :--- |
| 正常 | `---` 區塊 + 空行 + 正文 | 只有 `---` 之後的部分（含那個空行） |
| 正常 | 完全沒有 `---` 區塊 | 整個檔案 |
| 邊界 | 正文中間有一行 `---`（分隔線） | 那一行**留在正文裡** |
| 邊界 | 只有開頭的 `---`，沒有結尾的 `---` | 不視為 front matter，整個檔案都是正文 |
| 邊界 | 檔案第一行是空行，第二行才是 `---` | 不視為 front matter（front matter 只認檔頭） |
| 邊界 | `---\n---\n` 之後接正文（空的 front matter） | `---` 之後的部分；metadata 全部走 fallback |
| 邊界 | 檔案以 BOM 開頭，接著才是 `---` | 照樣認得 front matter，正文不含 BOM |
| 邊界 | 檔案用 CRLF 換行 | 正文保留 CRLF |
| 例外 | front matter 是壞的 YAML（縮排錯、重複鍵） | 照樣剝離（編輯區永遠看不到 `---`），metadata 走 fallback 並標記不完整 |

### 6.2 寬容解析 metadata（R-7）

| 情境 | front matter | 期望 |
| :--- | :--- | :--- |
| 正常 | 五個欄位齊全，`category`／`tags` 是清單 | 照實讀出 |
| 邊界 | `category: 技術筆記`（單一字串） | 讀成 `['技術筆記']` |
| 邊界 | `tags: electron`（單一字串） | 讀成 `['electron']` |
| 邊界 | 沒有 `category`／`tags` | 讀成空清單 |
| 邊界 | 清單裡混進非字串（`- 12`） | 那一項略過 |
| 例外 | 沒有 `title` | 標題用檔名去掉 `.md`，標記「metadata 不完整」 |
| 例外 | `title:`（空值）或 `title: "   "` | 同上 |
| 例外 | 檔名含非 ASCII（`台積電-法說會.md`） | fallback 標題保留原字元 |
| 邊界 | 有 `title` | **不**標記不完整 |

### 6.3 接回 front matter（R-6／R-8）

| 情境 | 動作 | 期望 |
| :--- | :--- | :--- |
| 正常 | 只換正文 | front matter 區塊**逐字不動**，正文換成新的 |
| 正常 | 換正文並更新 `updated_at` | 只有 `updated_at` 那一行的值變了；未知欄位、鍵順序、註解全部原位 |
| 邊界 | front matter 有註解在檔頭、在某個清單項目後面、在區塊最後一行 | 三個位置的註解都還在 |
| 邊界 | 寫入只有一個元素的 `category` | 寫成 YAML 清單（`- 技術筆記`），**不是** `category: 技術筆記`，也不是逗號字串 |
| 邊界 | 寫入空的 `category`／`tags` | 移除該鍵，而不是留下 `[]` |
| 邊界 | 檔案原本沒有 front matter，但被要求寫入欄位 | 建立一個 front matter 區塊，正文保持原樣 |
| 邊界 | 檔案用 CRLF | 接回去的 front matter 也用 CRLF |
| 例外 | front matter 是壞的 YAML，被要求存正文 | 正文照存，**壞的區塊逐字保留**（不重寫、不阻擋存檔） |

### 6.4 由標題產生檔名（R-9）

| 情境 | 標題 | 已存在的檔名 | 期望 |
| :--- | :--- | :--- | :--- |
| 正常 | `Zen of Writing` | — | `zen-of-writing.md` |
| 正常 | `Tauri 與 Electron 的取捨` | — | `tauri-與-electron-的取捨.md`（非 ASCII 保留） |
| 邊界 | `A/B 測試: 第一輪` | — | 檔名不合法字元移除 |
| 邊界 | `  好多   空白  ` | — | 空白收斂成單一 `-`，頭尾不留 `-` |
| 邊界 | `Zen of Writing` | 已有 `zen-of-writing.md` | `zen-of-writing-2.md` |
| 邊界 | `Zen of Writing` | 已有 `zen-of-writing.md`、`zen-of-writing-2.md` | `zen-of-writing-3.md` |
| 邊界 | `Zen of Writing` | 已有 `ZEN-OF-WRITING.md` | 視為衝突（檔案系統不分大小寫） |
| 例外 | `///` 或空字串 | — | `untitled.md` |

### 6.5 讀取的範圍檢查（§7.3 安全基線 + 地基切片留下的缺口）

| 情境 | 動作 | 期望 |
| :--- | :--- | :--- |
| 正常 | 讀 vault 內某 workspace 的某篇文章 | 讀得到內容與檔案修改時間 |
| 正常 | vault 本身位在一條符號連結之後（例如 macOS 的 `/var` → `/private/var`） | **照樣讀得到**（不能誤判成逃出 vault） |
| 例外 | 名稱本身會逃出 vault（`../secret.md`） | 拒絕，不讀任何檔案 |
| 例外 | vault 裡有一個檔案是符號連結，指向 vault 外面 | 拒絕（這是地基切片留下的缺口，本切片負責關掉） |
| 例外 | workspace 資料夾本身是符號連結，指向 vault 外面 | 拒絕 |
| 例外 | 檔案不存在 | 明確失敗，不回傳空字串當正文 |

## 7. 假設（需求文件留白處，本切片自行裁決）

| # | 空白 | 裁決 | 理由 |
| :--- | :--- | :--- | :--- |
| A-0 | 能保留註解與鍵順序的 YAML 依賴要由誰加進依賴清單（依賴清單被地基切片列為「沒有人可以改」） | **本切片加**，只加這一個，鎖 exact 版本 | 專案文件明文把 YAML／front matter 的處理指派給 front matter 切片；「沒有人可以改」指的是不要動建置／測試設定與既有版本鎖定。R-8 沒有這類套件做不到。**在 PR 說明大聲寫出來** |
| A-1 | front matter 的界定方式 | 檔案（可選的 BOM 之後）**第一行**必須正好是 `---`，後面必須再出現一行正好是 `---`；否則整個檔案都是正文 | 沒有結尾就吃掉整個檔案是資料災難；「第一行才算」符合 §2「檔開頭以 `---` 包夾」 |
| A-2 | 結尾 `---` 之後的空行算 front matter 還是正文 | **算正文**，只吃掉結尾 `---` 那一行自己的換行 | 這樣「讀出來→接回去」是逐位元相同。若為了畫面漂亮而修掉空行，等於每存一次檔就改寫使用者的檔案 |
| A-2a | 分隔線那兩行本身的行尾空白（`---  `、`---\t`） | **原樣寫回，而且兩行各自記住** | 同 A-2：什麼都沒要求改的寫入不該改到檔案。兩行分開記是因為只有一行有裝飾的檔案，用同一份寫回會把兩行拉成一樣（review 抓到的行為錯誤） |
| A-3 | 檔案開頭的 BOM | 保留，接回去時原樣重新寫出 | 不特別處理的話 `---` 認不出來，front matter 會漏進編輯區——那是 FR-4.1 的硬性違反 |
| A-4 | YAML 的 `...`（document end marker）算不算結尾 | **不算**，只認 `---` | §3.2 定義的是「以 `---` 包夾」 |
| A-5 | front matter 是壞的 YAML 時怎麼辦 | 照樣剝離；**整個區塊視為不可信**——欄位一律走 fallback 並標記不完整（不做「半讀」）；**寫回去時整個區塊逐字保留、絕不重新序列化** | YAML 函式庫對有錯誤的文件不保證能序列化（原實測會直接報錯）。兩害相權：寧可存不到 `updated_at`，也不能弄壞使用者的檔案，更不能因此讓正文存不進去 |
| A-6 | `title` 什麼情況算「缺失」 | 缺鍵、空值、空白字串、或不是字串（`title: 2026`）都算缺失 | 「標題是一段文字」是產品前提；讀到數字就當它是標題會在 UI 上更難解釋 |
| A-7 | `created_at`／`updated_at` 缺失時 | 讀成空字串，**不**因此標記「metadata 不完整」 | 通用語言地圖明定 `hasIncompleteMetadata` 的含義是「`title` 缺失、以檔名 fallback」。不擴張既有詞彙的定義 |
| A-8 | 「metadata 不完整」是否也涵蓋「front matter 壞掉」 | **涵蓋**（此時 `title` 本來也讀不出來，本質上就是 A-6 的情況） | 使用者看到的 UI 文案是「metadata 不完整」，這正是它 |
| A-9 | `category`／`tags` 清單裡的非字串項目 | 略過該項目 | 寬容解析的目的是「讀得懂人寫的東西」，不是把 `12` 變成標籤 |
| A-10 | 寫入空的 `category`／`tags` | 移除該鍵 | §3.2 說「可 0 到多個」，0 個最自然的表達就是這個鍵不存在。留 `[]` 是 Rustle 自己的痕跡 |
| A-11 | 只換正文時要不要重新序列化 front matter | **不要**，逐字保留原本的區塊 | 最強的 R-8 保證：沒被要求改的東西，連序列化器都不要碰它 |
| A-12 | YAML 序列化器重新序列化時無法保留的排版 | 至多接受三項正規化：行內註解前的多個空白收斂成一個、連續空行收斂成一個、flow 集合（`[a, b]`）括號內補一個空白。鍵、順序、註解內容、引號風格、未知欄位的值全部保留 | 實測結果。這三項是序列化器的行為，不是我們的選擇；把它寫下來比假裝沒有更誠實。實作時須以所選 YAML 函式庫重新實測，不得超出這三項。Rustle 產生的檔案本來就不會有這些排版 |
| A-13 | CRLF 檔案 | front matter 原本用 CRLF，接回去的區塊也用 CRLF；正文的換行原樣保留 | 序列化器只吐 `\n`。不補這一步，Windows 使用者的檔案每存一次就整段換行變樣 |
| A-14 | slug 的字元規則 | 轉小寫、空白收斂成 `-`、移除檔名不合法字元（`/ \ : * ? " < > |` 與控制字元）、`-` 收斂、頭尾 `-` 去掉、非 ASCII 保留、加上 `.md` | R-9 明文的規則，加上「連續 `-` 收斂」這個顯而易見的補充 |
| A-15 | slug 完全空掉（標題只有不合法字元） | `untitled.md` | 檔案總得有名字。這是技術性的最後防線，不是業務規則 |
| A-16 | 同名衝突的比對是否分大小寫 | **不分**（比對前一律轉小寫） | macOS 與 Windows 的檔案系統不分大小寫；分大小寫比對會產生「檢查說沒撞、建立時撞了」 |
| A-17 | 檔案不存在時怎麼回覆畫面層 | 讓檔案系統的錯誤往上傳，最後變成 `unexpected` 失敗 | 地基切片定案的四種失敗原因不為此擴張。檔案不存在在 UI 上不需要分流（清單上的文章不該不存在） |
| A-18 | 符號連結缺口（地基切片的 D-1）怎麼關 | 在**真的要碰檔案的那一刻**（infrastructure）把路徑透過檔案系統解析，再把解析後的位置交回 `VaultScope` 做包含判斷 | `realpath` 要檔案已存在，所以它天生屬於讀寫那一刻；包含判斷的規則仍然只住在 `VaultScope` 裡。domain 依然不直接碰檔案系統——解析能力以 `ISymbolicLinkResolver` 由 infrastructure 注入。**硬連結不在這個方法的能力之內**（見發佈檢查清單 S-3） |
| A-19 | 讀出來的檔案修改時間用什麼形狀 | ISO 8601 字串（`ArticleBody.lastKnownModifiedAt` 是字串） | 地基切片的契約已定；在邊界正規化成字串，domain 不必認識平台的時間型別 |

## 8. 已知不做、但要記錄的取捨

- **正文第一行可能是空行。** 依 A-2，`---` 之後的空行留在正文裡，所以編輯區的第一行通常是空的。這是為了逐位元的來回一致而付的代價；替代方案（讀的時候修掉、寫的時候補回來）會在「原本沒有空行」或「原本有兩行」的檔案上改寫使用者的內容。
- **`updated_at` 在 front matter 壞掉的檔案上不會被更新**（A-5）。可以接受：那個檔案本來就需要人去修，而正文照存。
- **本切片沒有 UI。** 使用者「看到編輯區只有正文」這件事要等 Wave 2 把清單與版面接上才觀察得到。本切片的驗收落在通道層與物件層。
